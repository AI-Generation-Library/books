# 09장. 파일럿 기획서 작성하기

파일럿은 작게 만든 운영 서비스가 아니다. 중요한 가정을 제한된 범위에서 확인하는 실험이다. 시연이 잘되었다는 이유만으로 서비스 범위를 확대하지 않도록, 시작 전에 무엇을 확인하고 어떤 결과에서 다음 단계로 갈지 합의해야 한다.

## 1. 확인할 가설과 비교 대상을 적기

가설에는 대상 업무, 변화시킬 단계와 확인할 결과를 포함한다. “AI가 잘 답한다”보다 “승인된 자료를 찾고 초안을 만드는 흐름이 기존 검색·작성 방식보다 작업 부담을 줄이면서 공개 범위 위반을 늘리지 않는가”처럼 비교할 수 있는 질문이 낫다.

비교 대상은 현재 업무일 수도 있고, 자료만 정비한 검색 방식일 수도 있다. 여러 개선을 동시에 적용한다면 어떤 결과를 AI의 효과라고 말할 수 있는지 제한해야 한다. 문서 정비와 교육까지 포함한 업무 개선 패키지의 효과로 보고할 수도 있다.

파일럿 기간과 사용자의 규모를 정한다. 작은 표본에서 확인할 수 없는 드문 사건이나 장기 효과는 별도로 남긴다. 실험의 목적과 무관한 데이터를 수집하거나 모든 부서를 참여시키는 것은 피한다.

## 2. 범위 안과 밖을 함께 정의하기

기획서에는 기능 목록보다 업무와 책임의 경계를 적는다. 어떤 문의 유형과 자료를 다룰지, 누가 초안을 검토할지와 어떤 행동을 하지 않을지를 설명한다. 예외는 기존 담당자에게 인계하는 경로를 포함한다.

| 항목 | 솔빛서비스의 가상 파일럿 |
| --- | --- |
| 대상 | 승인 자료로 설명 가능한 일반 고객 문의 |
| AI 역할 | 문서 검색, 근거 제시, 답변 초안 |
| 사람 역할 | 근거·공개 범위 확인, 수정, 외부 발송 승인 |
| 제외 | 계약 예외 자동 승인, 환불·계정 변경의 자동 실행 |
| 자료 | 소유자와 공개 등급을 확인한 제한된 문서 |
| 실패 시 | 기존 검색·작성 흐름으로 복귀, 담당자 인계 |

범위 밖의 요청을 어떻게 발견할지도 정한다. 사용자에게 안내만 해 두고 실제 시스템에서는 모든 자료와 도구를 열어 두면 경계가 유지되지 않는다. 권한과 인터페이스에서도 제한을 구현해야 한다.

## 3. 성공 조건을 한 지표로 줄이지 않기

성과에는 작업 시간, 품질, 사용 경험과 운영 부담을 함께 넣는다. 시간이 줄었어도 근거 없는 약속이나 내부 정보 공개가 늘면 확대할 이유가 부족하다. 평균 품질 점수와 중대한 실패를 분리한다.

초기 성공 기준은 기준선을 측정한 뒤 합의할 수 있다. 아직 근거가 없는 목표를 의도적으로 낮추거나 높여 확정하지 않는다. 안전·권한·승인과 같은 필수 조건은 성과 평균에 섞지 않고 진행 조건으로 둔다.

이 책의 가상 파일럿은 평가 중 발견된 중대한 정보 공개나 승인 우회를 즉시 보류 사유로 삼는 예시를 사용한다. 이는 조직의 예시 운영 기준이며 법률이나 외부 인증 기준을 대신하지 않는다. 평가 사례에서 실패가 없었다는 사실만으로 모든 실제 업무가 안전하다고 주장할 수 없다.

## 4. 중단 조건과 대응을 먼저 정하기

중단 조건은 실패를 숨기지 않게 만드는 장치다. 예산 초과, 반복되는 근거 오류, 운영자의 과도한 부담이나 필수 권한 통제의 실패가 나타나면 실험을 보류하거나 범위를 줄일 수 있다. 확인한 원인과 개선 작업이 있으면 다시 시작할 조건을 정한다.

누가 실험을 중단할 수 있는지, 중단 후 사용자를 어떻게 안내할지와 처리 중인 업무를 누가 이어받을지 적는다. 급한 업무를 멈추면서 아무 대안도 제공하지 않으면 사용자와 고객이 피해를 볼 수 있다. 기존 업무 방식으로 돌아갈 수 있는 경로를 유지한다.

종료 이후 자료와 계정도 정리한다. 실험용 데이터의 보관·삭제, 접근 권한의 회수, 결과 기록과 비용 정산을 기획서에 포함한다. 파일럿이 끝난 뒤 비공식 운영 서비스가 남지 않도록 한다.

## 5. 책임·시간·산출물을 연결하기

파일럿에는 업무 책임자, 시스템 담당자, 자료 소유자, 품질 검토자와 사용자 대표가 필요하다. 모든 역할을 별도의 사람에게 맡길 필요는 없지만, 한 사람이 여러 역할을 맡으면 검토 시간과 승인 독립성을 고려한다.

회의 횟수보다 확인할 산출물을 정한다. 문제 정의서, 자료 목록, 업무 흐름, 평가 사례, 운영·중단 절차와 결과 보고서가 기본이다. 각 산출물의 소유자와 검토자를 지정하면 일정 지연이 어디에서 생기는지 확인하기 쉽다.

```text

기간·예산·운영 시간:

```

기획서를 읽은 다른 사람이 같은 실험 범위를 설명할 수 있는지 확인한다. “보안 검토 필요”라는 항목에는 실제로 확인할 데이터와 전달 경로, 검토자와 완료 조건을 붙인다. 승인 여부를 추측한 상태로 시작하지 않는다.

## 점검 질문과 정리

- 파일럿이 확인할 질문과 비교 대상이 명확한가?
- 중단 결정의 권한과 기존 방식으로 돌아가는 경로가 있는가?
- 종료 후 남길 것과 정리할 것이 정해져 있는가?

파일럿 기획서는 성공을 선언하는 문서가 아니라 검증과 책임의 약속이다. 다음 부에서는 이를 실제 업무 흐름과 사용자 경험으로 구체화한다.
