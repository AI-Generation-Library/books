# 19장. 기존 업무 시스템과 연결하기

AI 기능을 별도 화면에 만들면 시연은 쉽지만 담당자는 정보를 복사하고 결과를 다시 입력해야 할 수 있다. 기존 시스템과 연결하면 업무 부담을 줄일 수 있는 대신 인증, 데이터 경계와 실패 처리가 중요해진다. 연결의 목적은 모델에 모든 권한을 주는 것이 아니라 필요한 업무 단계를 안전하게 이어주는 것이다.

## 1. 연결 지점을 최소화하기

솔빛서비스의 첫 연결은 사건 조회, 승인 자료 검색과 내부 초안 저장이다. 기존 고객 발송 기능은 담당자가 사용한다. 각 연결은 별도의 서비스 계정과 최소 권한을 검토하고 사용자의 사건 접근 권한을 서버에서 확인한다.

모델에게 데이터베이스 접속 정보나 운영 비밀을 전달하지 않는다. 모델이 정한 SQL이나 URL을 그대로 실행하는 대신 허용된 기능과 입력 스키마를 가진 API로 감싼다. 임의 주소 접근은 내부 자원이나 외부 공격 대상으로 연결될 수 있으므로 대상 범위를 제한한다.

## 2. 시스템 간 계약을 정의하기

API 계약은 필수 입력, 반환값, 오류 코드와 시간 제한을 포함한다. 요청 사건 ID가 잘못되었는지, 권한이 없는지, 일시 장애인지 구분한다. 사용자에게 보여줄 메시지는 비밀이나 다른 고객 사건의 존재를 노출하지 않게 설계한다.

| 상황 | 내부 처리 | 업무 화면 |
| --- | --- | --- |
| 인증 만료 | 재인증 요구, 실행 중단 | 다시 로그인 안내 |
| 사건 권한 없음 | 접근 차단·필요 로그 | 허용된 담당 경로 안내 |
| 검색 시간 초과 | 제한된 재시도·기존 검색 | 지연과 대체 방법 표시 |
| 초안 형식 오류 | 저장 차단·인계 | 초안 확인 실패 표시 |
| 중복 저장 요청 | 요청 ID로 상태 확인 | 실제 저장 상태 표시 |

성공 상태는 실제 저장이나 실행 결과를 확인한 뒤 표시한다. 모델이 “저장했습니다”라고 쓴 문장을 성공 판정으로 사용하지 않는다.

## 3. 비동기 작업의 상태를 드러내기

오래 걸리는 작업은 접수, 진행, 완료, 실패, 취소와 부분 완료를 구분한다. 브라우저를 닫았다고 서버 작업이 자동 취소되는지, 재접속 후 상태를 조회할 수 있는지 정한다. 재실행과 이어하기가 같은 행동인지도 구분해야 한다.

한 작업의 문서·프롬프트·모델·권한 버전을 묶어 기록한다. 중간에 정책이 바뀌면 기존 결과를 그대로 이어갈지 재검증할지 결정한다. 권한이 철회된 경우 과거 작업이 계속 자료를 읽지 못하도록 현재 권한을 다시 확인한다.

## 4. 비밀과 운영 설정을 관리하기

API 키는 서버의 승인된 비밀 저장 방식이나 로컬 실행의 환경 변수처럼 범위에 맞는 경로를 사용한다. 저장소, 프롬프트, 브라우저 로그와 공유 화면에 넣지 않는다. 키의 생성·회수·교체 책임자를 정하고 테스트용과 운영용을 분리한다.

개인 키로 로컬 도구를 사용하는 것과 조직의 공용 서비스를 운영하는 것은 다르다. 조직 서비스에는 사용자 인증, 사용량 할당과 비용 책임이 필요하다. 클라이언트가 임의로 보낸 권한이나 비용 정보를 신뢰하지 않는다.

## 5. 관측과 단계적 적용

요청 추적 ID로 접수부터 검색·생성·저장까지 연결한다. 지연은 단계별로 나누고 실패 원인을 기록한다. 관측을 위해 모든 대화를 저장할 필요는 없다. 필요한 메타데이터와 비식별화된 오류 정보부터 설계한다.

처음에는 일부 담당자와 문의 유형에서 읽기 중심으로 적용한다. 장애 시 AI를 끄더라도 기존 접수·발송 흐름이 작동해야 한다. 전환과 복귀를 연습하고 담당자가 결과 상태를 오해하지 않는지 확인한다.
