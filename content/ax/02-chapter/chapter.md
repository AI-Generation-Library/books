# 02장. 업무에 필요한 AI 기술 지도

회의에서 “우리도 생성형 AI를 써야 한다”는 의견이 나온다. 고객 이탈을 예측하는 문제, 문의 내용을 정리하는 문제와 결재 금액을 검증하는 문제는 모두 업무 개선에 해당하지만 같은 기술로 해결해야 하는 것은 아니다. 기술 지도를 읽는 목적은 유행하는 도구를 많이 아는 데 있지 않다. 문제를 나누고 적합한 방법과 검증 기준을 선택하는 데 있다.

## 1. 입력·판단·출력을 먼저 분해하기

기술 이름을 정하기 전에 입력의 종류와 원하는 출력을 적는다. 표 형식의 거래 이력에서 다음 달 수요를 예측하는지, 문서에서 근거를 찾아 설명하는지, 사진 속 결함 후보를 표시하는지에 따라 접근이 달라진다. 업무의 성공 기준도 예측 오차, 근거의 정확성, 누락 여부처럼 달라진다.

| 접근 | 잘 맞는 문제의 예 | 준비할 것 | 확인할 것 |
| --- | --- | --- | --- |
| 규칙·일반 프로그램 | 합계 계산, 명시적 승인 한도 검사 | 규칙과 예외 정의 | 계산 정확성, 경계 조건 |
| 예측·분류 모델 | 수요 예측, 문서 분류, 이상 징후 탐지 | 대표 데이터와 목표 정의 | 오류 유형, 데이터 변화 |
| 생성형 AI | 초안 작성, 요약, 설명, 정보 추출 | 맥락과 지시, 검토 기준 | 사실성, 누락, 표현의 적합성 |
| 검색과 생성의 결합 | 사내 자료를 근거로 답변 | 문서 품질, 권한, 검색 구조 | 검색 근거와 답변의 일치 |
| 멀티모달 처리 | 이미지·음성·텍스트가 섞인 업무 | 매체별 품질과 이용 권한 | 인식 오류와 결합 오류 |

표는 기술을 배타적으로 나누는 규칙이 아니다. 문의 분류는 규칙, 전통적 분류 모델 또는 생성형 AI로 구현할 수 있다. 실제 선택에서는 데이터의 양과 품질, 필요한 응답 시간, 운영 비용과 검증 가능성을 함께 비교한다.

## 2. 생성형 AI와 예측 모델의 평가가 다른 이유

예측 모델은 정해진 목표에 대한 수치나 범주를 출력하도록 설계할 수 있다. 과거 데이터의 정답과 비교해 오류를 측정할 수 있지만, 데이터가 과거를 대표한다고 해서 앞으로도 같은 성능을 보장하지는 않는다. 업무 환경이 바뀌면 입력 분포와 결과의 의미가 변할 수 있다.

생성형 AI의 문장에는 여러 평가 축이 있다. 표현이 자연스러워도 중요한 조건을 누락하거나 문서에 없는 사실을 덧붙일 수 있다. 문장 유사도만으로 업무 품질을 평가하기 어렵다. 어떤 주장이 근거에 있어야 하는지, 어떤 표현은 금지해야 하는지와 예외 시 어떻게 응답해야 하는지를 정해야 한다.

언어 모델이 계산을 설명할 수 있다는 사실과 계산 결과가 정확하다는 사실도 구분해야 한다. 금액, 날짜, 수량처럼 결정적으로 검증할 수 있는 항목은 일반 프로그램이나 검증 규칙으로 확인하는 것이 유용하다. AI가 입력을 구조화하고 기존 프로그램이 계산하며 사람이 결과를 승인하는 흐름을 만들 수 있다.

## 3. 멀티모달은 정보를 늘리고 오류 경로도 늘린다

고객이 스크린샷과 음성 설명을 함께 보낸다면 텍스트만 처리하는 흐름보다 많은 정보를 활용할 수 있다. 그러나 작은 글씨, 잘린 화면, 배경 소음과 잘못된 음성 인식은 다른 오류를 만든다. 매체를 추가할 때는 어떤 단계에서 정보를 잃거나 오해할 수 있는지 확인해야 한다.

파일에 고객 정보나 내부 시스템 화면이 포함되어 있을 수도 있다. 매체를 모델에 전달하기 전에 이용 권한과 전달 범위를 정한다. 음성을 문자로 변환한 결과도 원본을 완전히 대체한다고 가정하지 않는다. 중요한 계약 조건이나 식별 정보는 확인 가능한 원본과 비교할 절차가 필요하다.

## 4. 검색·추론·실행을 구분하기

문서를 찾는 일, 문서의 내용을 바탕으로 답을 제안하는 일과 실제 업무 시스템을 바꾸는 일은 서로 다른 권한을 요구한다. 같은 모델을 사용하더라도 도구와 시스템 권한에 따라 위험이 달라진다.

솔빛서비스의 첫 파일럿은 승인된 지식 자료에서 근거를 검색하고 답변 초안을 만드는 범위다. 고객에게 이메일을 보내거나 계약 조건을 변경하는 권한은 주지 않는다. 답변 초안의 품질을 확인하기 전에 실행 권한까지 넓히지 않도록 설계한다. 검색 기반 응답과 에이전트의 구체적인 구조는 17장과 18장에서 다룬다.

기술을 여러 개 연결할 때는 각 단계의 실패를 따로 측정한다. 분류가 틀려 자료를 잘못 찾았다면, 답변 문장만 고치는 것으로 원인이 해결되지 않는다. 데이터 수집, 분류, 검색, 생성, 검증과 승인 중 어느 단계에서 실패했는지 기록해야 한다.

## 5. 도입 방식과 기술 범주를 혼동하지 않기

완성형 서비스를 구매하는지, API를 사용하는지, 모델을 자체 운영하는지는 도입 방식이다. 그 안에서 사용하는 기술과 업무 설계는 별도의 결정이다. 완성형 제품이라도 데이터와 권한을 설정하고 결과를 평가해야 하며, 자체 구축이라고 해서 모든 문제를 원하는 대로 해결할 수 있는 것은 아니다.

처음에는 작은 비교표를 만든다. 동일한 가상 입력을 사용해 규칙 기반 처리, 기존 검색, AI를 활용한 처리의 결과와 검토 시간을 비교한다. 시연의 속도만 비교하지 말고 설정·갱신·오류 처리에 필요한 운영 부담도 적는다. 계정별 모델 접근 권한, 데이터 처리 조건과 실제 가격은 해당 제공자의 현재 문서와 계약에서 확인한다. 이 책은 특정 모델의 순위나 가격을 고정하지 않는다.

## 직접 해 보기: 기술 선택 메모

```text
대상 문제:
입력: 표 / 문서 / 이미지 / 음성 / 혼합
출력: 수치 / 분류 / 설명 / 초안 / 시스템 변경
오류를 확인할 정답 또는 근거:
비교할 기존 방식:
검토할 기술 조합:
필요한 데이터와 권한:
운영자가 유지할 설정:
실패 시 기존 방식으로 돌아가는 경로:
```

선택한 기술이 없더라도 문제를 처리할 수 있는 간단한 대안을 하나 적는다. 그 대안과 비교해야 AI 도입의 가치를 설명할 수 있다. 기술 선택은 이후의 데이터 점검과 파일럿 평가에서 다시 바뀔 수 있다.

## 점검 질문과 정리

- 계산처럼 별도 프로그램으로 검증할 항목은 무엇인가?
- 입력 매체를 늘리면 새로 생기는 오류와 권한 문제는 무엇인가?
- 검색, 답변 제안과 실제 실행을 구분했는가?

기술 지도는 문제를 나누는 도구다. 가장 복잡한 기술을 고르는 대신 필요한 기능과 검증 가능한 경계를 찾는다. 다음 장에서는 기술 범주와 관계없이 반드시 다뤄야 할 AI의 불확실성을 살펴본다.
