# 18장. AI 에이전트와 업무 자동화

에이전트는 목표를 수행하기 위해 도구를 선택하고 결과에 따라 다음 행동을 이어가는 구성이다. 검색 한 번과 초안 한 번으로 끝나는 흐름보다 유연할 수 있지만, 잘못된 판단이 여러 행동으로 확대될 수 있다. 필요한 자율성만 부여하고 실행 경계를 시스템으로 제한해야 한다.

## 1. 정해진 흐름과 에이전트를 비교하기

단계가 명확한 업무에는 고정된 워크플로가 이해와 검증에 유리하다. 정해진 양식을 읽고 필수 항목을 확인하는 일에 매번 도구 선택을 맡길 필요는 없다. 반면 문의에 따라 추가 자료와 확인 순서가 달라지는 업무에는 제한된 에이전트 구성이 도움이 될 수 있다.

에이전트라는 이름보다 어떤 상태를 읽고 어떤 행동을 실행하는지 적는다. 읽기, 내부 초안 저장, 외부 전송, 금전·권한 변경을 분리한다. 읽기 전용 도구로 시작해도 민감한 자료 조회와 로그 노출 위험은 남는다.

## 2. 도구 계약을 작성하기

도구에는 이름, 목적, 입력 스키마, 허용 대상, 실행 계정, 출력, 실패와 승인 조건이 필요하다. 모델이 만든 인수는 서버가 검증한다. 허용되지 않은 고객 ID나 주소, 범위를 벗어난 금액을 도구가 그대로 실행해서는 안 된다.

| 도구 | 허용 범위 | 실행 전 확인 |
| --- | --- | --- |
| 승인 자료 검색 | 사용자 권한 안의 현재 자료 | 신원·조직·공개 목적 |
| 문의 조회 | 배정된 고객 문의 | 사건 접근 권한 |
| 초안 저장 | 현재 사건의 내부 초안 | 스키마·길이·근거 ID |
| 외부 발송 | 첫 파일럿에서 제공하지 않음 | 별도 과제에서 재설계 필요 |
| 계약·계정 변경 | 첫 파일럿에서 제공하지 않음 | 기존 승인 절차 유지 |

프롬프트에 도구를 사용하지 말라고 쓰는 것보다 도구 자체를 제공하지 않거나 서버가 금지하는 것이 분명하다. 도구 결과 안의 문장도 신뢰할 수 없는 참고 데이터일 수 있다.

## 3. 승인할 행동을 구체적으로 보여주기

승인은 “계속할까요?”가 아니라 대상, 변경 내용, 외부 영향과 근거를 보여주는 단계여야 한다. 승인 후 인수가 바뀌면 다시 확인해야 한다. 사용자가 본 내용과 실행되는 행동을 연결하는 식별자나 해시를 사용할 수 있다.

일괄 승인은 편리하지만 어떤 행동이 포함되는지 불분명하면 통제가 약해진다. 취소, 만료와 역할 변경을 고려한다. 읽기 지원을 승인한 사용자의 행동이 송금이나 외부 이메일까지 포괄한다고 해석하지 않는다.

## 4. 반복과 비용을 제한하기

에이전트가 같은 도구를 반복하거나 실패를 계속 재시도할 수 있다. 최대 단계 수, 시간, 호출 횟수와 예산을 설정한다. 제한에 도달하면 지금까지 확인한 내용과 미완료 작업을 남기고 중단한다. 중단을 숨기고 성공으로 기록하지 않는다.

외부 조치에는 재시도와 중복 실행을 고려한다. 응답을 받지 못했다고 실제 실행이 실패한 것은 아니다. 요청 식별자, 멱등성 처리와 상태 조회로 중복을 막는다. 되돌릴 수 없는 행동은 자동 재시도보다 상태 확인과 담당자 인계가 우선일 수 있다.

## 5. 실행 흔적을 업무 단위로 남기기

기록에는 사건 ID, 사용자 권한, 도구와 인수의 필요한 부분, 승인, 결과 상태와 버전을 남긴다. 비밀과 개인정보 원문은 최소화한다. 모델의 긴 설명보다 어떤 도구가 무엇을 실행했는지 확인할 수 있어야 한다.

솔빛서비스는 첫 단계에서 자료 검색과 초안 저장만 제공한다. 후속 단계에서 자동화 범위를 넓히려면 별도 평가와 승인 기준이 필요하다. 도구 호출이 기술적으로 가능하다는 사실은 업무상 실행 권한을 의미하지 않는다.

## 실습: 행동을 한 단계씩 허용하기
