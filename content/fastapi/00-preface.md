API 하나를 만드는 데 필요한 코드는 길지 않다. 하지만 운영에서 중요한 질문은 코드 길이와 관계가 없다. 왜 DB 응답이 느려지면 건강 검사까지 지연되는가? 왜 워커를 늘렸는데 DB가 더 자주 멈추는가? 왜 응답을 보냈는데 트랜잭션은 실패하는가? 왜 사용자 A의 검색 결과가 사용자 B의 AI 답변에 섞이는가?

이 책은 이 질문에 답할 수 있는 실행 모델을 만드는 데 초점을 둔다. 라우터, 검증 모델, DB 세션, 이벤트 루프, 외부 API, 작업 큐를 각각 외우기보다 요청 하나가 어떤 자원을 언제 점유하고 언제 반환하는지 추적한다. 그 모델이 있으면 새 라이브러리를 도입해도 실패 지점을 예측할 수 있다.

## 독자와 선수 지식

Python의 함수·클래스·예외를 읽을 수 있고 HTTP 요청과 JSON을 경험한 독자를 가정한다. Java와 Spring Boot, JavaScript와 Express.js 경험자는 비교 설명을 통해 기존 지식을 연결할 수 있다. Python 자체가 처음이라면 4장의 타입 표기와 6장의 코루틴을 읽기 전에 함수 호출, 제너레이터, 컨텍스트 매니저를 작은 프로그램으로 익히자.

프레임워크 경험은 필수가 아니다. 다만 이 책은 모든 프로그래밍 입문 문법을 설명하지 않으며, PostgreSQL 설치나 클라우드 계정 생성까지 대신하지 않는다. 필요한 외부 구성요소와 명령은 각 장에서 구분한다.

## 실습의 기술 기준

| 항목 | 기준 | 이유 |
|---|---|---|
| Python | 3.12 이상, 본문은 3.12 문법 기준 | `TaskGroup`, `asyncio.timeout`, 최신 타입 표기를 사용 |
| FastAPI | 0.121 이상, 1 미만 | 의존성 `scope` 설명에 필요한 최소 버전 |
| Pydantic | 2.x | `model_dump`, `field_validator`, `model_validator` 사용 |
| SQLAlchemy | 2.x | `select`, `Mapped`, `AsyncSession` 사용 |
| DB | PostgreSQL을 운영 설계의 기준으로 사용 | 트랜잭션·벡터 검색·다중 인스턴스 설명 |
| 로컬 통합판 | SQLite 및 모의 AI 구성 | 외부 계정이나 모델 호출 비용 없이 전체 흐름 확인 |

이 범위는 예제의 설계 기준이다. 모든 가능한 패키지 조합의 호환성을 보장하는 버전 잠금은 아니다. 설치 후 테스트에 통과한 환경은 별도의 고정 의존성 파일로 보관하자. FastAPI가 요구하는 Starlette 범위는 설치 도구가 해결하도록 두고 임의의 Starlette 버전을 따로 강제하지 않는다. 최신판이라는 표현과 특정 날짜의 배포판이라는 표현도 구별한다.

## 예제 표기 읽기

**완전 실행 예제**는 설치할 패키지와 파일명이 있고, 그 코드만으로 해당 실습을 실행할 수 있다. **기존 파일 변경**은 앞에서 만든 코드의 어느 부분을 바꾸는지 설명한다. **개념 예제**는 제어 흐름이나 설계 경계를 보여주며 제품 구현 전체가 아니다. 작은 예제의 메모리 저장소, 모의 모델, 단일 프로세스 제한은 본문에서 밝힌다.

본문의 성능 숫자는 측정 절차를 설명하는 가정이나 예시인 경우가 많다. 실제 측정이라고 표시하지 않은 숫자를 보장 성능으로 읽지 말자. 컴퓨터, 데이터, 요청 분포, 연결 재사용, 워커 수가 바뀌면 결과도 달라진다. 검증한 코드 범위와 외부 시스템 검증 여부는 [검증 안내](appendices/verification.md)에 기록한다.

명령은 기본적으로 `python -m ...` 형태를 사용한다. Windows PowerShell에서는 `curl` 별칭 대신 `curl.exe`를 쓰거나 `Invoke-RestMethod`를 사용한다. Linux/macOS에서는 `curl`을 사용하면 된다. 운영 예제에 등장하는 Docker·k6·Nginx는 해당 도구가 설치된 환경에서 실행한다.

## 책을 관통하는 서비스

Knowledge Hub 사용자는 문서를 올리고 자신의 문서에서 답을 찾는다. 서버는 문서 소유권을 검사하고 텍스트를 분할한다. 작업자는 검색 인덱스를 구성한다. 질문을 받으면 접근 가능한 문서만 검색하고, 근거와 함께 답변을 만든다. 긴 실행은 작업 ID로 관리하고 이벤트 스트림으로 진행 상태를 전달한다.

이 단순한 이야기는 대부분의 백엔드 문제를 포함한다. 파일 업로드에는 크기 제한이 필요하고, DB 쓰기에는 트랜잭션이 필요하다. 질문마다 모델을 호출하면 비용이 발생한다. 여러 사용자가 동시에 질문하면 외부 API 한도와 서버 자원이 충돌한다. Agent가 도구를 실행하면 사용자 승인과 실행 이력이 필요해진다.

모든 장을 처음부터 읽는 경로가 가장 안정적이다. 이미 CRUD 개발에 익숙하다면 5~8장, 11장, 17장, 20장, 24장을 먼저 읽고 자신의 기존 서비스를 분석해 보자. 마지막 프로젝트에서 중요한 것은 데모 화면보다 사용자 격리, 실패 후 상태, 취소 후 자원 정리다.

## 실습 습관

매 장에서 먼저 실행 결과를 예측하고 실제 결과와 비교하자. 성공하는 입력 외에 없는 ID, 잘못된 자료형, 느린 외부 응답, 두 개의 동시 요청을 넣는다. 결과를 설명할 수 없다면 코드를 더 추가하기 전에 타임라인을 그린다. 요청 시작, 대기 시작, 대기 종료, 응답 시작, 자원 반환을 표시하면 대부분의 오해가 드러난다.

공식 문서 링크는 API의 계약과 버전별 차이를 확인하기 위해 제공한다. 본문의 예제와 설계 과제는 이 책의 학습 흐름에 맞춰 작성한 것이다. 문서를 읽을 때는 함수 이름뿐 아니라 실패·취소·종료 조건까지 확인하는 습관을 갖자.
