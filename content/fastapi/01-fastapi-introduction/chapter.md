> PART 1. FastAPI 시작하기

## 학습 목표와 출발점

이 장을 마치면 웹 서버와 웹 프레임워크의 책임을 구분하고, FastAPI를 구성하는 라이브러리의 역할을 설명할 수 있다. 다른 프레임워크와 비교할 때 처리량 하나보다 팀의 문제와 운영 조건을 기준으로 판단한다.

회사 내부 문서를 검색하는 서비스를 만든다고 생각해 보자. 처음에는 검색 결과를 JSON으로 반환하면 충분하다. 곧 사용자 인증, 문서 업로드, 느린 검색, 실시간 답변이 필요해진다. FastAPI는 이 요구를 Python 함수와 명시적인 데이터 계약으로 표현하기 좋다. 그러나 DB 설계나 운영 안정성을 자동으로 해결하지는 않는다. 프레임워크 선택과 서비스 설계는 서로 다른 판단이다.

## 1.1 웹 프레임워크와 API 서버의 역할

브라우저나 모바일 앱은 TCP 연결 위에서 HTTP 메시지를 보낸다. 서버는 메서드, 경로, 헤더, 본문을 읽고 응답 상태와 데이터를 반환한다. 네트워크 바이트를 읽는 일과 비즈니스 규칙을 실행하는 일은 분리할 수 있다. 이 분리가 서버 교체와 애플리케이션 테스트를 가능하게 한다.

웹 서버는 연결을 받고 프로토콜을 처리한다. 웹 프레임워크는 `/documents/42`를 문서 조회 함수에 연결하고, 입력을 검증하고, 예외를 응답으로 바꾼다. 서비스 계층은 요청자가 문서를 읽을 수 있는지, 삭제해도 되는지를 판단한다. 저장 계층은 SQL과 트랜잭션을 다룬다. 한 함수에 모두 넣을 수는 있지만, 책임이 섞이면 실패 원인을 찾기 어려워진다.

API 서버의 출력은 화면이 아니라 다른 프로그램이 소비할 계약이다. `200` 응답의 필드명 변경은 화면 문구 변경보다 영향이 클 수 있다. 클라이언트가 기존 필드를 파싱하기 때문이다. 따라서 API 설계는 엔드포인트뿐 아니라 자료형, 누락 가능성, 오류 응답과 버전 정책을 함께 정의하는 작업이다.

## 1.2 FastAPI의 특징과 설계 철학

FastAPI에서는 함수의 매개변수와 타입 표기가 API 계약의 중심이 된다. `document_id: int`는 읽는 사람에게 정수 ID를 기대한다는 뜻이고, 프레임워크에는 요청값을 변환하고 검증할 단서가 된다. Python의 타입 힌트 자체가 모든 실행을 강제하는 것은 아니다. FastAPI와 Pydantic이 해당 정보를 이용해 경계에서 검사한다.

이 접근의 이점은 계약의 중복을 줄이는 데 있다. 요청 모델을 정의하면 검증과 OpenAPI 스키마 생성이 그 모델을 함께 사용한다. IDE의 자동완성도 개선된다. 하지만 스키마가 생겼다고 비즈니스 규칙까지 검증된 것은 아니다. 문자열 길이는 모델에서 검사해도 문서 소유권은 인증된 사용자와 저장소를 확인해야 한다.

FastAPI는 비동기 I/O를 표현할 수 있고 동기 함수를 함께 지원한다. `async def`라는 표기만으로 더 빠른 서비스가 되지는 않는다. 느린 함수 안에서 이벤트 루프를 막으면 같은 프로세스의 다른 요청까지 영향을 받는다. 이 책의 5~8장이 문법보다 실행 구조를 강조하는 이유다.

## 1.3 Flask, Django, Express.js, Spring Boot와 비교

아래 표는 선택을 돕기 위한 구조 비교다. 프레임워크의 절대적인 속도 순위나 프로젝트별 생산성 보장은 아니다.

| 프레임워크 | 익숙한 출발점 | 선택 시 검토할 질문 |
|---|---|---|
| Flask | 작은 Python 라우터와 확장 조합 | 검증·인증·문서화 규칙을 팀이 얼마나 직접 구성할 것인가? |
| Django | ORM, 인증, 관리자 기능을 포함한 통합 체계 | 관리 화면과 관계형 데이터 중심 업무가 핵심인가? |
| Express.js | JavaScript 미들웨어 조합 | Node 생태계와 프런트엔드 언어 통일이 중요한가? |
| Spring Boot | Java의 타입 체계와 통합된 애플리케이션 구성 | 기존 JVM 인프라·조직 규칙·복잡한 업무 도메인과 얼마나 연결되는가? |
| FastAPI | Python 타입 기반의 API 계약과 ASGI | Python 생태계와 외부 I/O·스트리밍을 결합해야 하는가? |

Flask나 Django의 실행 방식도 배포 서버와 버전에 따라 달라진다. Django를 무조건 동기 전용이라고 설명하거나 Spring을 항상 요청당 스레드 하나라고 단정하면 현재의 다양한 구성을 놓친다. 여기서는 FastAPI의 기본 ASGI 모델을 기준으로 비교하고, 다른 프레임워크의 세부 실행 구조는 선택한 배포 방식의 공식 문서에서 확인한다.

Express에서 `req.body`를 직접 읽고 검증 미들웨어를 조합해 본 독자라면 FastAPI의 요청 모델이 계약을 한 곳에 모으는 장점을 느낄 수 있다. Spring의 Controller·Service·Repository에 익숙한 독자는 Python에서도 같은 책임 분리가 가능하다는 점을 기억하면 된다. 폴더 이름을 그대로 옮기는 것보다 예외와 트랜잭션의 경계를 옮기는 것이 중요하다.

## 1.4 FastAPI, Starlette, Pydantic, Uvicorn의 관계

일반적인 구성에서 Uvicorn은 ASGI 서버, Starlette는 웹 처리 기반, Pydantic은 데이터 모델 검증, FastAPI는 타입 기반 API 선언과 의존성 해결을 담당한다. FastAPI의 기반 관계는 [공식 기능 설명](https://fastapi.tiangolo.com/features/)에서 확인할 수 있다.

```text
클라이언트
  → Uvicorn: 연결·HTTP 처리
  → ASGI 호출
  → Starlette 기반 미들웨어·라우팅
  → FastAPI: 입력 검증·의존성 해결·엔드포인트 실행
  → Pydantic을 이용한 응답 계약 검사/직렬화
  → ASGI 응답 메시지
  → Uvicorn → 클라이언트
```

이 그림은 책임을 이해하는 개념 흐름이다. 실제 구현에서는 모델 검증과 라우팅 객체가 연결되어 있고, 모든 응답이 같은 검증 경로를 거치는 것은 아니다. 직접 `Response`를 반환하면 일반 응답 모델 처리와 달라진다. 이 차이는 4장에서 다룬다.

`FastAPI()` 객체를 만드는 것은 포트 8000을 여는 것과 다르다. 그 객체는 요청을 처리할 애플리케이션이다. Uvicorn이 그 객체를 가져와 포트를 열고 호출해야 외부 요청을 받을 수 있다. 이 분리 덕분에 테스트에서는 실제 포트를 열지 않고도 애플리케이션을 호출할 수 있다.

## 1.5 FastAPI가 적합한 서비스 유형

외부 API와 DB를 기다리는 시간이 긴 서비스, Python 데이터 처리 생태계를 활용하는 서비스, 명시적인 JSON 계약이 필요한 서비스에서 FastAPI는 좋은 후보가 된다. 문서 검색 API, 모델 호출 중계 서버, 내부 데이터 플랫폼, 모바일 백엔드가 이에 해당한다.

반대로 CPU를 지속적으로 사용하는 대형 추론을 API 프로세스 안에서 그대로 수행하면 웹 동시성의 이점을 잃기 쉽다. 이때 FastAPI는 요청 접수와 작업 상태 조회를 담당하고, 계산은 작업자나 추론 서버로 분리할 수 있다. 프레임워크를 바꾸기 전에 책임 배치를 바꾸는 것이 더 효과적인 경우가 많다.

팀이 이미 특정 ORM·배포 체계·감사 정책에 깊이 투자했다면 새 프레임워크 도입 비용을 계산해야 한다. 파일럿에서는 개발 시간뿐 아니라 장애 재현, 로그 추적, 권한 검증, 의존성 업데이트도 측정한다. 개발자가 좋아하는 문법과 조직이 안정적으로 운영할 수 있는 시스템은 함께 평가해야 한다.

## 내부 원리: 선언 시점과 요청 시점

다음 코드는 실행 방법보다 두 시점을 구분하기 위한 개념 예제다.

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok"}
```

모듈을 가져올 때 `app`이 생성되고 데코레이터가 함수와 경로를 등록한다. 아직 HTTP 요청은 없다. 나중에 `/health` 요청이 도착하면 등록된 함수를 호출한다. 데코레이터 아래의 코드가 서버 시작 때마다 요청처럼 실행된다고 생각하면 설정과 네트워크 연결을 잘못 배치하기 쉽다.

`health`는 동기 함수다. FastAPI가 엔드포인트로 호출하는 동기 함수에는 동시성 처리 규칙이 적용된다. 그러나 개발자가 다른 함수 안에서 `health()`를 직접 호출하면 평범한 Python 호출이다. 프레임워크가 모든 함수 호출을 가로채는 것은 아니다.

## 기본 실습: 첫 서버의 책임 관찰

**완전 실행 예제.** Python 3.12 환경에서 별도 폴더를 만들고 다음 패키지를 설치한다. 환경 격리는 2장에서 자세히 다룬다.

```powershell
python -m pip install "fastapi>=0.121,<1" "uvicorn>=0.30,<1"
```

`main.py`에 다음을 저장한다.

```python
from fastapi import FastAPI

app = FastAPI(title="Knowledge Hub — 시작")

@app.get("/health")
async def health() -> dict[str, str]:
    return {"status": "ok"}

@app.get("/documents/{document_id}")
async def read_document(document_id: int) -> dict[str, int | str]:
    return {"id": document_id, "title": "첫 문서"}
```

```powershell
python -m uvicorn main:app --reload
```

다른 터미널에서 요청한다.

```powershell
Invoke-RestMethod 'http://127.0.0.1:8000/health'
Invoke-RestMethod 'http://127.0.0.1:8000/documents/7'
```

첫 요청은 `status=ok`, 두 번째는 `id=7`을 반환한다. `/documents/abc`는 정수 변환에 실패해 검증 오류 응답을 반환한다. 브라우저에서 `/docs`를 열면 같은 경로의 입력 계약을 확인할 수 있다. 이 문서는 DB에 실제 문서 7이 존재한다는 사실을 보장하지 않는다. 현재 코드는 가상의 문서를 만들어 반환한다.

터미널에서 서버를 종료한 뒤 같은 URL로 요청해 보자. 코드 파일은 남아 있지만 연결은 실패한다. 애플리케이션의 존재와 서버 프로세스의 실행이 다르다는 것을 직접 관찰하는 실습이다.

## 실무 적용과 성능·주의사항

서비스를 선택할 때 먼저 가장 느린 의존성을 적는다. 검색 DB가 300ms 걸리고 애플리케이션이 5ms 쓰는 상황을 가정하면, Python 함수 몇 줄을 줄여도 전체 응답은 크게 달라지지 않는다. 반대로 이벤트 루프를 100ms 막는 코드가 있으면 그 영향은 다른 요청으로 확산될 수 있다. 수치는 가정이지만 원인 구분은 실제 설계에 필요하다.

건강 검사는 빠르고 예측 가능해야 한다. 프로세스가 살아 있는지 확인하는 liveness와 요청을 받을 준비가 되었는지 확인하는 readiness는 역할이 다르다. 모든 검사가 느린 외부 API까지 호출하도록 만들면 외부 장애가 재시작 폭주를 만들 수 있다. 22장에서 배포와 함께 구체화한다.

자동 문서화는 명세 검토를 쉽게 만들지만 보안을 대신하지 않는다. 문서에 없는 경로라도 인증이 없으면 호출할 수 있다. 응답 DTO, 객체 권한, 비밀 관리, 요청 제한은 별도로 설계해야 한다.

## 확인 문제와 해설

1. `app = FastAPI()`를 실행했지만 브라우저가 연결하지 못한다. 무엇을 확인할 것인가?
2. 모델 호출 시간이 대부분을 차지하는 API에서 프레임워크의 단순 벤치마크 순위가 덜 중요한 이유는 무엇인가?
3. 정수 경로 검증과 문서 조회 권한 검사의 차이를 설명하라.
4. 실습: `/version`을 추가하고 반환 필드를 `/docs`에서 확인하라.

**해설.** 1번은 ASGI 서버 프로세스 실행, 모듈 경로, 포트와 바인딩 주소를 확인한다. 2번은 전체 지연과 자원 점유가 외부 모델에 의해 결정될 수 있기 때문이다. 3번은 전자가 입력 형식 계약이고 후자가 사용자와 객체 사이의 권한 규칙이기 때문이다. 4번의 완료 기준은 서버 요청 성공, JSON 구조 확인, 문서 경로 등록 확인이다. 실제 배포 버전은 하드코딩한 문자열이 아니라 빌드 식별자와 연결한다.

## 요약과 다음 장

FastAPI는 API 계약과 요청 처리를 연결하는 도구다. 서버, 프레임워크, 데이터 검증의 책임을 분리해서 이해하면 실행과 장애를 설명할 수 있다. 다음 장에서는 이 코드를 다른 컴퓨터에서도 재현할 수 있도록 개발 환경을 구성한다.
