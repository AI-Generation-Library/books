## 학습 목표와 도입 사례

AI 서비스의 용량을 HTTP 요청 수만으로 표현하지 않고 생성 슬롯, 토큰 예산, 대기열, SSE 연결, GPU 메모리로 나누어 계산한다. 여러 인스턴스에서 제한과 세션을 일관되게 관리하고, 비용·지연·품질을 함께 검증하는 부하 실험을 설계한다. 목표 숫자는 가정과 실측을 명확히 구분한다.

Knowledge Hub의 일반 문서 조회 API는 충분히 빠른데 AI 질의만 밤마다 느려진다. CPU 사용률은 낮고 API 인스턴스를 두 배로 늘려도 개선되지 않는다. 생성 슬롯은 이미 모두 사용 중이며 대기열만 늘고 있다. 이때 API 서버 증설은 접수 속도를 올리지만 답변 처리량은 거의 바꾸지 못한다. 먼저 어느 자원의 처리량이 제한인지 파악해야 한다.

## 28.1 LLM 호출과 서버 처리량의 관계

AI 요청의 CPU 사용 시간이 짧아도 외부 호출이 오래 유지되면 in-flight 요청 수가 많아진다. 안정적인 정상 상태에서 평균 동시 작업 수는 대략 도착률과 평균 체류 시간의 곱이다. 예를 들어 초당 20건, 평균 4초는 약 80건의 동시 작업이라는 계획 가정이다. 대기 시간이 늘어 전체 체류 시간이 12초가 되면 240건이 된다. 이 값은 실제 서버의 벤치마크가 아니라 Little의 법칙을 적용한 용량 검토다.

요청 수 제한과 토큰 처리량 제한은 다르다. 질문 20개가 각각 짧은 답변을 생성하는 상황과 긴 보고서를 생성하는 상황은 같은 RPS로도 자원을 다르게 사용한다. 모델의 request/minute와 token/minute 제한을 따로 관리하고 입력 길이·최대 출력에 따른 예약을 적용한다. 긴 요청 때문에 짧은 요청이 모두 기다리지 않도록 작업 등급별 대기열과 공정성 정책을 검토한다.

용량 계획에는 완료율을 사용한다. 접수 API가 초당 1,000건을 반환하지만 모델 작업은 초당 10건만 완료한다면 나머지 작업은 매초 990건씩 쌓인다. 큐는 병목을 제거하는 장치가 아니라 순간적인 차이를 흡수하는 저장소다. 지속적인 과부하는 제한, 일정 조정, 공급자 용량 변경, 모델 선택 변경 같은 정책으로 해결한다.

## 28.2 동시 LLM 요청 제한

프로세스 세마포어는 한 프로세스의 동시 작업만 제한한다. 인스턴스 네 개에 각각 20슬롯을 두면 전체는 80슬롯이 된다. 공급자 전체 제한이 40이라면 배치 배분이나 분산 limiter가 필요하다. 분산 limiter는 임대 만료와 프로세스 장애를 처리해야 하고, 제한 시스템 장애 때 무제한 실행할지 보수적으로 거절할지 정책을 갖는다.

접수와 실행 제한을 나눈다. 접수는 사용자별 활성 작업 수와 대기열 상한을 확인한다. 실행은 모델별 슬롯과 예상 토큰 예산을 획득한다. 줄을 서 있는 요청도 메모리를 소비하므로 세마포어 앞에서 무한 대기하도록 두지 않는다. 즉시 질의에는 짧은 대기 상한을, 배치 업무에는 명시적인 완료 예상과 deadline을 제공한다. capacity를 초과하면 429 또는 503으로 거절하고 클라이언트가 다시 시도할 기준을 안내한다.

아래는 **완전 실행 예제** `capacity_demo.py`다. 표준 라이브러리만 사용한다. 순간적으로 100건이 도착하고 대기열은 16건, 워커는 4개라는 제한을 보여 준다. 공급자 없는 모의 I/O이며 실제 모델 처리량을 측정하는 프로그램은 아니다.

```python
import asyncio
import time


async def main():
    queue = asyncio.Queue(maxsize=16)
    active = 0
    maximum = 0
    completed = 0

    async def worker():
        nonlocal active, maximum, completed
        while True:
            item = await queue.get()
            try:
                active += 1
                maximum = max(maximum, active)
                await asyncio.sleep(0.02)
                completed += 1
            finally:
                active -= 1
                queue.task_done()

    workers = [asyncio.create_task(worker()) for _ in range(4)]
    accepted, rejected = 0, 0
    started = time.monotonic()
    # No await in this producer loop: it deliberately models an instantaneous burst.
    for request_id in range(100):
        try:
            queue.put_nowait(request_id)
            accepted += 1
        except asyncio.QueueFull:
            rejected += 1
    await queue.join()
    for task in workers:
        task.cancel()
    await asyncio.gather(*workers, return_exceptions=True)
    assert completed == accepted == 16
    assert rejected == 84 and maximum <= 4
    print({"accepted": accepted, "rejected": rejected,
           "completed": completed, "max_active": maximum,
           "seconds": round(time.monotonic() - started, 3)})


if __name__ == "__main__":
    asyncio.run(main())
```

**실행:** `python capacity_demo.py`. accepted/completed는 16, rejected는 84이며 max_active는 4를 넘지 않는다. elapsed는 장비와 스케줄러에 따라 달라진다. 모든 요청을 무조건 성공시켰다는 결과보다, 제한을 지키고 승인된 작업을 완료한다는 결과가 이 실습의 목적이다. 큐 크기와 워커 수를 바꾸면서 대기 시간과 거절 정책이 어떻게 달라지는지 기록한다.

## 28.3 모델 API Rate Limit 대응

공급자 제한을 만나기 전에 서비스가 예약 기반 속도 제어를 적용한다. 응답의 429와 Retry-After, 공급자 요청 ID를 기록하고 새로운 호출을 잠시 줄인다. 요청마다 독립적으로 재시도하면 제한이 풀리는 순간 또 폭주한다. 모델/계정 단위로 제한 신호를 공유하고 jitter를 적용한다. 이미 전달된 결과의 재시도는 25장의 중복 비용과 스트림 계약을 따르도록 한다.

한 공급자 제한을 피하려고 다른 모델로 자동 전환할 때도 검증이 필요하다. 개인정보 처리 지역, 출력 계약, 문맥 길이, 도구 지원, 품질, 가격이 달라질 수 있다. 제품이 허용한 fallback 목록 안에서만 전환하고 사용자에게 필요한 차이를 설명한다. 공급자 장애 때 긴 대기열을 유지할지 실패를 빠르게 알릴지 업무 유형별로 결정한다.

rate limit 회복을 성공 요청 수 하나로 판단하지 않는다. p95 대기 시간, 재시도율, 요청당 실제 토큰, 결과 불명 비율을 함께 본다. 남은 deadline이 짧은 작업은 늦게 재시도해도 사용자에게 도움을 주지 못한다. 예약을 유지한 채 무한히 기다리지 않도록 job deadline을 만료 처리하고 가능한 작업만 이어 실행한다.

## 28.4 SSE 연결 수와 메모리 사용량

SSE 연결은 대부분 대기하지만 공짜 자원이 아니다. 소켓, ASGI Task, TLS 상태, 프록시 버퍼, 구독 큐가 메모리를 사용한다. 사용자당 64 KiB 버퍼라는 가정으로 10,000개를 계산하면 약 625 MiB이고, 여기에 Python 객체·네트워크·기본 프로세스 메모리가 더해진다. 버퍼가 메시지 개수 기준이라면 큰 delta 하나 때문에 실제 바이트가 훨씬 커질 수 있다.

버퍼 상한은 개수와 바이트를 함께 고려한다. 느린 클라이언트가 상한을 넘으면 최신 snapshot으로 전환하거나 연결을 종료하고 재접속 안내를 보낸다. 영속 이벤트 저장소가 있으면 워커가 느린 구독자에게 직접 묶일 필요가 없다. SSE는 “생성된 이벤트를 배달하는 연결”로 취급하고 작업 수행과 분리한다. 완료 작업에는 불필요하게 연결을 유지하지 않는다.

프록시 buffering, idle timeout, heartbeat 간격도 end-to-end로 확인한다. 애플리케이션이 yield해도 프록시가 묶어서 전달하면 사용자는 실시간으로 보지 못한다. 브라우저 기본 EventSource는 임의 Authorization 헤더를 넣는 사용에 제약이 있으므로 쿠키·짧은 구독 티켓·fetch 기반 스트림 중 적절한 방식을 선택한다. 접근 토큰을 URL에 넣으면 로그와 기록에 노출될 수 있다. 짧은 구독 티켓이라도 범위·만료·재사용 정책을 갖는다.

SSE의 인증 시점도 설계한다. 최초 검증 후 몇 시간 연결하면 토큰 만료와 권한 철회를 언제 반영할지 결정해야 한다. 연결 최대 수명을 두고 재인증하게 하거나 정책 변경 이벤트로 구독을 닫는다. 작업을 취소하는 정책과 단순 구독 종료는 구분한다. 재접속 폭주를 피하려면 클라이언트 재시도에 jitter를 적용하고 gateway에서 접수 제한을 둔다.

## 28.5 Redis 기반 응답 캐싱

캐시 키에는 tenant/사용자 권한 범위, 정규화 질문, 문서 인덱스 버전, 모델 버전, 프롬프트 버전, 출력 설정을 포함한다. 대화 맥락이 답변을 바꾼다면 해당 맥락의 안정적인 해시도 필요하다. 질문 하나만 키로 쓰면 다른 조직의 같은 질문에 같은 답을 반환할 수 있다. 캐시 값의 근거 ID를 최종 접근 정책으로 검증하는 방어도 유용하다.

생성 결과 캐시는 비결정적 출력을 고정한다. 이것이 제품 요구에 맞는지 확인한다. 개인 맞춤 답변이나 시간에 민감한 정책은 TTL이 짧아야 하거나 캐시하면 안 될 수 있다. 문서 삭제와 ACL 변경은 시간만 기다리는 TTL보다 적극적인 무효화가 필요하다. 캐시 키에 인덱스·권한 버전을 넣으면 오래된 값을 조회하지 않는 방식을 만들 수 있지만 저장 공간 정리는 별도다.

동시 cache miss에서는 같은 질문을 여러 번 생성하지 않도록 singleflight 또는 짧은 락을 적용한다. 분산 락 만료만으로 외부 생성의 exactly once를 보장하지 않는다. 생성 시간이 lease보다 길면 두 실행이 겹칠 수 있다. 캐시 갱신과 비용 원장에는 별도 run/operation ID를 남기고, 락을 해제할 때는 자신이 보유한 token을 비교한다. 실패 결과 캐시는 짧게 적용해 장애 때 호출 폭주를 줄이되 영구 실패처럼 보이지 않게 한다.

## 28.6 LLM 작업 큐 설계

job은 DB의 업무 기록이고 큐 메시지는 그 job을 실행할 신호다. 큐에 질문과 비밀 정보를 모두 복사하기보다 job ID와 필요한 버전만 전달한다. 워커는 DB에서 권한과 상태를 확인하고 claim한다. 작업 접수와 outbox를 같은 트랜잭션으로 저장하고 발행기·소비자는 중복 메시지를 가정한다. 최종 상태를 커밋하기 전에 ACK하면 작업을 잃을 수 있다.

Redis Streams 소비자 그룹은 pending 항목과 ACK를 관리할 수 있다. ACK가 업무 DB 결과 커밋을 대신하지 않으며 pending reclaim 이후 중복 실행이 가능하므로 애플리케이션 멱등성이 필요하다. 데이터 보존, persistence, replication, reclaim 정책은 사용한 Redis 버전에 맞춰 검증한다. [Redis Streams 공식 문서](https://redis.io/docs/latest/develop/data-types/streams/), [XPENDING](https://redis.io/docs/latest/commands/xpending/)

업무별 queue를 분리하면 작은 실시간 질의가 긴 문서 ingestion 뒤에 밀리는 일을 줄일 수 있다. 단순 FIFO만 사용하면 한 조직의 대량 배치가 모든 사용자에게 지연을 줄 수 있다. 사용자·조직별 활성 작업 상한과 weighted fair scheduling을 검토한다. 우선순위가 높아도 낮은 등급이 영원히 굶지 않도록 aging 또는 최소 처리량을 적용한다.

dead-letter queue는 실패를 숨기는 곳이 아니다. 반복 실패 원인과 최종 오류를 저장하고 재처리 권한·조건을 정의한다. payload나 권한이 바뀌었으면 같은 작업을 억지로 되살리기보다 새 버전의 job을 만들 수 있다. 수동 재처리도 기존 operation ID와 비용 원장을 확인해야 한다. 운영자가 클릭했다고 중복 실행 정책이 사라지지 않는다.

## 28.7 GPU 추론 서버와 FastAPI 연동

FastAPI를 서비스 gateway로 두고 모델 추론은 별도 서버에서 수행할 수 있다. gateway는 인증·문서 권한·예산·작업을 담당하고 추론 서버는 모델 메모리와 배치·생성 스케줄링을 담당한다. CPU용 Uvicorn worker를 늘리는 것과 GPU 처리량을 늘리는 것은 다르다. 모델을 모든 API worker에 적재하면 GPU 메모리 복사본이 늘어 out-of-memory가 발생할 수 있다.

vLLM 같은 추론 서버는 HTTP 인터페이스를 제공하지만 지원 엔드포인트와 인증 범위는 실제 설치 버전에 맞춰 확인해야 한다. 서비스망 내부에서도 gateway를 우회해 추론 서버에 접근할 수 없게 네트워크와 인증을 적용한다. 여기서는 실제 GPU 서버를 실행하거나 모델을 내려받지 않는다. [vLLM 공식 serving 문서](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)

성능 검토에는 입력 prefill과 출력 decode, KV cache, 배치 크기, 최대 문맥 길이를 포함한다. 긴 문맥을 제한 없이 허용하면 작은 요청의 TTFT까지 악화될 수 있다. 배치를 늘리면 처리량이 좋아져도 개별 지연이 늘 수 있으므로 목적에 맞는 지표를 선택한다. 모델 워밍업과 readiness를 분리하고 새 인스턴스가 준비되기 전에 트래픽을 보내지 않는다. 모델 버전과 양자화 변경은 성능뿐 아니라 품질 평가를 거친다.

## 28.8 다중 인스턴스 환경의 세션 관리

세션·작업·이벤트를 프로세스 메모리에만 두면 다음 요청이 다른 인스턴스에 도착했을 때 이력이 사라진다. sticky session은 단기 최적화일 수 있지만 장애 복구를 제공하지 않는다. 대화 소유권과 job은 공유 DB에, 이벤트는 재생 가능한 저장소에, 실시간 fan-out 신호는 필요에 따라 Redis에 둔다. Pub/Sub만 사용하면 구독이 끊긴 동안 이벤트를 잃을 수 있다.

인스턴스 종료 때 접수를 멈추고 기존 연결을 drain한다. 장기 Agent는 checkpoint를 저장한 뒤 안전한 지점에서 lease를 반납한다. 강제 종료를 정상 종료와 같은 것으로 가정하지 말고 다음 워커가 복구할 절차를 둔다. SSE 클라이언트는 재접속 cursor로 이어 받고 중복 event ID를 제거한다. DB나 큐의 상태가 일시적으로 불일치하면 snapshot endpoint로 최종 상태를 확인할 수 있게 한다.

## 28.9 AI 서비스 부하 테스트

모의 공급자로 서버 한계를 측정하는 테스트와 실제 추론 환경에서 품질·생성 성능을 측정하는 테스트를 구분한다. 모의 공급자는 지연 분포, 429, 부분 스트림 실패, 타임아웃, 취소를 재현할 수 있다. 서버의 admission control과 복구를 비용 없이 반복 검증한다. 실제 공급자 시험은 계약과 예산 범위 안에서 별도 수행한다.

k6 시나리오에는 접수 도착률, 작업 완료 확인, SSE 연결 유지, 재접속, 대량 업로드를 나눈다. closed workload에서 사용자가 응답을 기다리면 서버가 느려질수록 도착률도 낮아져 과부하를 숨길 수 있다. arrival-rate 방식으로 목표 접수를 유지하는 시험도 필요하다. 부하 생성기의 CPU·소켓·네트워크가 먼저 포화되지 않았는지 확인한다. [k6 scenarios 공식 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/)

테스트 결과에 허용/거절률, queue age, 완료 p95, TTFT, 모델 재시도율, 비용 상한, SSE 버퍼와 연결 수를 포함한다. 거절 요청을 성공 latency 통계에서 지우고 “p95가 좋다”고 결론내리면 운영 품질을 왜곡한다. overload에서 정상 사용자에게 얼마나 예측 가능한 실패를 제공했는지까지 평가한다. 복구 이후 backlog가 감소하는지도 관찰한다.

## 28.10 비용, 지연시간, 처리량 최적화

최적화 순서는 측정한 병목에 따라 정한다. 검색 컨텍스트 중복 제거는 입력 비용과 생성 지연을 함께 줄일 수 있다. 출력 상한은 비용을 줄이지만 답변 완성도가 떨어질 수 있다. 캐시는 반복 질문에 효과적이고, 작은 모델 routing은 간단한 작업에 유용할 수 있으나 품질 회귀를 검증해야 한다. 성공한 한 사례만으로 전체 모델을 변경하지 않는다.

세 목표는 서로 연결되지만 동일하지 않다. 큰 배치는 처리량을 올리면서 TTFT를 늘릴 수 있고, 더 좋은 재순위화는 생성 오류를 줄이지만 요청 지연을 추가한다. 제품이 중요하게 보는 품질 하한과 지연·비용 상한을 먼저 정하고 실험 결과를 그 경계로 비교한다. 변경 전후에 같은 데이터·트래픽 분포를 사용하고 모델·프롬프트·인덱스 버전을 기록한다.

## 확인 문제와 해설

1. API 인스턴스를 두 배로 늘렸는데 생성 완료율이 같은 이유는? **해설:** 외부 모델 슬롯·토큰 제한 또는 GPU가 병목일 수 있다. API CPU와 생성 단계 지표를 나눠 확인한다.
2. 프로세스별 세마포어 10은 전체 동시성 10을 보장하는가? **해설:** 아니다. 프로세스·인스턴스 수만큼 총 허용량이 늘어난다. 전체 배분이나 분산 제한이 필요하다.
3. SSE 메모리를 연결당 큐 100개로 제한하면 충분한가? **해설:** 메시지 크기가 다를 수 있다. 바이트 상한, 소켓·Task·프록시 비용까지 측정한다.
4. 부하 실습의 평가 기준은? **해설:** 상한을 지키고 승인된 작업을 완료하며 거절·취소·재접속을 정확히 집계해야 한다. 모의 sleep 결과를 실제 모델 벤치마크로 제시하면 실패다.
