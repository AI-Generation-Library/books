# 28장. 실험 설계와 실패 원인 분석

## 학습 목표

- 변수·snapshot·평가셋을 고정해 개선 원인을 찾는다.
- 검색 실패와 생성 실패를 분리한다.

## 단계를 따라 실패를 좁힌다

먼저 원문에 필요한 사실이 있는지 본다. 파싱본에도 남아 있는지, 청크 경계가 조건을 보존했는지, 권한 범위에서 검색 후보에 들어왔는지, 최종 컨텍스트에 포함되었는지 확인한다. 마지막으로 모델이 그 근거를 올바르게 사용했는지 본다.

정답 문서가 전혀 색인되지 않았는데 리랭커를 바꾸거나, 컨텍스트에 충분한 근거가 있는데 임베딩만 바꾸는 실험은 원인을 놓칠 수 있다. 질문별 trace를 통해 가장 먼저 깨진 단계를 찾는다.

## 고정할 것과 바꿀 것

```text
고정: 문서 snapshot, 권한, 질문 split, 평가 코드
변수: 청킹 또는 임베딩 또는 검색 방식 등 한 단계
기록: 설정 hash, 모델 파일 hash, 후보/근거 ID, 지표, 비용, 지연
```

한 번에 바꾸는 변수를 제한하고, 기법 하나를 빼 보는 ablation으로 이득의 원인을 확인한다. 여러 개를 결합한 최종 시스템이 좋아도 각각이 필수라는 결론은 나오지 않는다. 상호작용이 의심되면 통제된 조합 실험을 추가한다.

## 실제 작은 관측의 해석

dev 네 질문에서 신경망 dense MRR은 0.75, BM25와 hybrid는 1.0이었다. test에는 답변 가능한 질문 두 개와 거절 질문 두 개가 있어 순위 평균과 거절 정확도의 분모가 다르다. 작은 결과를 전체 한국어 문서 검색의 성능 비교로 확장하지 않는다.

이 사례는 벡터 검색을 도입했다는 사실보다 실제 질문 분포와 기준선이 중요하다는 학습 자료다. 모델이 새롭거나 파이프라인이 복잡하다는 이유로 더 높은 점수를 만들어 적지 않는다. 실패한 순위를 그대로 남겨 개선 가설을 세운다.

## 통계와 회귀

표본 수가 작으면 한 질문의 순위 변화가 평균을 크게 바꾼다. 충분한 자료에서는 같은 질문의 전후 차이와 불확실성을 추정하고 유형별 결과도 본다. 반복 실행을 독립적인 사용자 표본처럼 세지 않는다.

배포 전에 고정 평가셋으로 회귀를 검사하고, 중요한 보안·삭제·정답 사례는 실패 시 중단 조건으로 둔다. 품질이 조금 올랐지만 비용·지연이 크게 늘면 목표에 맞는 선택인지 판단한다. 모든 변경에서 test를 반복적으로 최적화하지 않도록 새 평가 구간을 유지한다.

## 실습과 평가

appendices/neural-results.json을 질문별로 읽고 dense dev의 첫 관련 순위가 낮은 사례를 찾는다. 같은 문서·query·권한에서 BM25 결과와 비교한다.

기본 테스트는 저장소 교체·삭제·권한·인용 실패의 회귀를 확인한다. 검색 점수의 자동 통계와 독립 사람 평가의 결과는 다른 증거로 보관한다.
