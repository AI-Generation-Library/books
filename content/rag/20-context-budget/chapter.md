# 20장. 컨텍스트 구성과 토큰 예산

## 학습 목표

- 검색 후보와 최종 생성 근거를 분리한다.
- 길이·순서·압축의 영향을 측정한다.

## 검색 순위가 곧 프롬프트는 아니다

검색 후보에는 겹치는 청크·부분적으로 관련된 설명·서로 다른 버전이 들어갈 수 있다. 그대로 모두 붙이면 잡음과 비용이 늘고 중요한 조건이 묻힐 수 있다. 컨텍스트 구성은 관련성·중복·충분성·길이를 함께 고려해 생성기에 제공할 근거를 정하는 단계다.

검색 top-20과 생성에 넣는 3개 근거는 서로 다른 예산이다. 리랭커·문서별 제한·부모 확장 후 실제 길이가 달라질 수 있다. 최종 프롬프트에 어떤 텍스트가 들어갔는지 별도로 추적해야 검색 로그와 생성 실패를 연결할 수 있다.

## 예산을 계산하는 단위

```text
전체 컨텍스트 제한
  ≥ 시스템 지시 + 사용자 질문 + 대화 이력
    + 자료 구분자/메타데이터 + 근거 텍스트 + 출력 예약량
```

토큰 수는 실제 생성 모델의 토크나이저로 계산한다. 문자 수나 파일 바이트를 그대로 토큰 수라고 부르지 않는다. 서비스의 기본 budget=1200은 교육용 문자 예산이다. Ollama 호출의 num_ctx=4096과 같은 단위가 아니다. 긴 실제 문서를 다루려면 모델별 토큰 계산과 절단 정책을 추가한다.

예제는 하나의 청크를 중간에서 임의로 자르지 않고 예산 안에 들어오는 청크를 선택한다. 부분 절단으로 인용 조건이 사라지는 것을 줄이는 단순 정책이다. 큰 첫 청크만으로 예산을 채우거나 필요한 근거를 건너뛸 수 있으므로 더 정교한 선택은 평가가 필요하다.

## 순서와 긴 컨텍스트

중요 근거의 위치·유사 문서의 반복·긴 잡음은 모델의 활용에 영향을 줄 수 있다. 긴 컨텍스트를 지원한다는 명세와 모든 위치의 근거를 동일하게 활용한다는 보장은 다르다. 모델·질문·근거 위치를 바꾼 실험으로 확인한다.

최신 문서를 먼저 두거나 가장 관련된 근거를 앞에 두는 정책은 선택지다. 충돌 자료의 유효 시점과 출처 우선순위는 단순 배치 순서로 해결하지 않는다. 정책에 따라 판별하고 해결하지 못하면 충돌을 명시한다.

## 압축과 요약의 손실

발췌형 압축은 관련 구간만 고르고, 생성형 압축은 모델이 문장을 다시 쓴다. 생성형 요약은 수치·부정·예외를 바꿀 수 있다. 압축 전 원문과 대응을 유지하고 최종 인용은 원문으로 연결한다.

비용을 줄였지만 답변에 필요한 조건이 사라졌다면 좋은 최적화가 아니다. 입력 토큰·지연과 함께 근거 포함률·인용 충실성·최종 정답을 평가한다. 압축 모델 호출 비용까지 총합에 넣는다.

## 실습과 평가

Engine.answer의 budget을 1로 바꾼 테스트는 context_budget 거절을 확인한다. 정상 budget에서 어떤 근거가 들어갔는지 출처와 비교한다.

같은 문서에 길고 관련 없는 문단을 추가해 정답 근거가 뒤로 밀릴 때를 별도 dev 실험으로 만든다. 실제 토크나이저 기반 상한은 구현 범위와 검증 기록을 따로 남긴다.
