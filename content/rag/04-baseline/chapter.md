# 04장. 문제 정의와 기준선 세우기

## 학습 목표

- 사용자 질문을 평가 가능한 요구사항으로 바꾼다.
- 복잡한 기법 도입 전에 비교할 기준선을 만든다.

## 챗봇이라는 요구를 분해한다

누가 어떤 문서를 근거로 무엇을 묻는지 정한다. 정확한 규정 조항 조회, 여러 문서 비교, 전체 주제 요약, 최신 수치 조회는 다른 문제다. 한 문장 답변이 충분한지, 표와 인용이 필요한지, 근거가 없을 때 무엇을 할지도 계약에 포함한다.

답변 정확도뿐 아니라 권한 누출 0건, 삭제 반영 기한, 허용 지연, 질문당 비용, 사람이 확인할 수 있는 인용 위치를 성공 기준으로 둔다. 숫자는 실제 요구와 검증 환경에서 정해야 하며 일반적인 보편 임계값을 베끼지 않는다.

## 비교 가능한 기준선

검색 없이 모델이 답하는 방식, 관련 문서 전체를 직접 입력하는 방식, BM25 검색 후 답하는 방식을 작은 기준선으로 만든다. 정답과 실행 비용을 같은 입력에서 비교한다. 복잡한 파이프라인을 먼저 만들면 어떤 단계가 실제 이득을 줬는지 알기 어렵다.

실습은 7개 가상 문서를 제공한다. 그중 관리자 전용과 다른 tenant의 문서는 공개 reader에게 보이면 안 된다. 평가 질문 8개는 dev 4개와 test 4개로 나누었다. test에는 답이 없는 질문과 권한 때문에 답할 수 없는 질문도 포함한다.

## 평가의 출발점

질문에는 관련 문서 ID와 관련성 등급인 qrels를 붙인다. 답이 없는 질문에 억지로 관련 문서를 지정하지 않는다. 답을 할 수 있는 질문의 순위 지표와 답할 수 없는 질문의 거절 성능을 나눠 본다.

이 데이터는 저자가 만든 작은 교육용 fixture다. 테스트라는 split 이름을 붙였다고 독립적인 산업 벤치마크가 되는 것은 아니다. 같은 저자가 문서와 질문을 만들었고 표본도 작으므로 실제 사용자 품질을 추정하지 않는다. 24장에서 더 큰 평가셋과 사람 검수 설계를 다룬다.

## 바꾸는 변수를 제한한다

청킹·임베딩·검색 방식·후보 수·리랭커·프롬프트를 한꺼번에 바꾸면 원인을 분리하기 어렵다. 우선 동일 문서 snapshot과 질문에서 BM25·dense·hybrid를 비교한다. 이후 한 변수씩 바꾸고 질문별 결과를 남긴다.

좋은 실험 기록은 모델 이름 외에 전처리·chunk 크기·오버랩·검색 후보 수·최종 근거 수·권한·버전·실행 시점을 포함한다. 임계값을 test 결과를 보며 반복 조정하면 평가셋에 맞춘 과적합이 생긴다. 탐색은 dev에서 하고 새로운 test로 재확인한다.

## 실습과 평가

`python -m ragbook.cli evaluate --split dev --mode bm25`와 `--mode hybrid`를 실행한다. 기본 문자 벡터 결과를 신경망 검색 결과로 부르지 않는다.

기계 판독 평가 결과는 부록에 제공한다. 이번 실제 다국어 모델 실험에서 dense의 dev MRR이 BM25보다 낮았던 사실도 함께 기록했다. 이 결과는 해당 작은 데이터와 설정의 관측이며 모델 전체의 우열이 아니다.
