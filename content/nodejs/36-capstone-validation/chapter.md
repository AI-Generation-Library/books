# 36장. 성능 검증부터 배포와 장애 대응까지

## 학습 목표

- 검증한 사실과 아직 확인하지 않은 범위를 구분한다.
- 측정·배포·복구 절차를 다음 사람이 재현할 수 있게 남긴다.

## 완료 기준을 기능과 운영으로 나눈다

책의 로컬 완료 기준은 원고·목차·메타데이터가 일치하고, 제공 예제가 선언한 환경에서 실행되며, 실패 경계 테스트가 통과하는 것이다. 실제 서비스 공개 기준에는 외부 서비스 통합·컨테이너·TLS·비밀 주입·백업 복원·부하·장애 복구 검증이 추가된다.

이 책은 실행한 검사만 성공으로 기록한다. `production` 모드 구현이나 Compose 파일이 존재한다는 사실과 그 환경에서 실행·운영 검증을 마쳤다는 사실을 구분한다. [검증 기록](../appendices/verification.md)이 실제 결과의 원본이다.

## 기본 검증 순서

```sh
npm ci --ignore-scripts
npm test
npm run typecheck
```

다른 터미널에서 서버를 시작한 뒤 smoke를 실행한다. 작업 결과를 확인하고 로그아웃 후 접근 거부도 테스트한다. 부하 도구는 먼저 `/health/live` 같은 단순 경로로 동작을 확인하고, 실제 용량은 인증·업로드·DB·큐가 연결된 업무 흐름으로 측정해야 한다.

메모리 모드 localhost 부하 결과는 네트워크·TLS·DB·Redis를 포함하지 않는다. 샘플 수가 적은 p99는 불안정할 수 있다. 측정한 수치를 클라우드 처리량이나 운영 SLA로 홍보하지 않는다. 조건·입력·오류·분포를 그대로 기록한다.

## 장애 시나리오 표

| 상황 | 기대 동작과 확인할 것 |
| --- | --- |
| 로그인 폭주 | KDF 동시성·요청 제한, 정상 요청 영향 |
| 업로드 중 연결 종료 | 스트림 중단·부분 파일 정리·작업 상태 |
| Redis 중단 | outbox 보존·readiness·복구 후 전달 |
| worker 중단 | 대기열 증가·재시작 후 재처리 |
| DB 중단 | 기한 내 실패·풀 대기 제한·비밀정보 미노출 |
| 프로세스 강제 종료 | stalled 재실행·파일/DB 정합성 점검 |
| 배포 중 SSE 종료 | 클라이언트 재연결·최신 상태 복구 |

이는 추가 실행 계획이며 모든 행을 이번 환경에서 시험했다는 목록이 아니다. 장애 주입은 테스트 전용 서비스와 데이터에서 수행하고 시작·복구·잔여 데이터 상태를 남긴다.

## 운영 문서와 복구

사용 버전·시작 명령·환경 변수 이름·헬스 체크·로그 위치·데이터 보관·백업·복원 절차를 작성한다. worker가 처리하지 못하는 작업은 원인 확인 후 재처리하고, 이미 완료된 외부 부수 효과를 중복 수행하지 않게 한다.

백업 성공 로그보다 복원 후 인증·업로드·처리·조회가 실제로 동작하는지 확인하는 것이 중요하다. DB·큐·파일이 서로 다른 시점의 스냅샷이라면 정합성 점검 절차가 필요하다. 복구 시간과 데이터 손실 허용 범위는 서비스 요구사항으로 정한다.

## 기여 가능한 결과로 정리

원고는 Markdown, 예제는 소스와 잠금 파일, 출처는 공식 링크와 생성 기록으로 남긴다. 생성된 DB·캐시·토큰·진단 파일·node_modules는 제출하지 않는다. 저장소 검사와 실행 결과를 PR에 적고, 검수하지 않은 범위도 숨기지 않는다. 다음 사람이 책을 개선할 수 있는 정보까지가 기여의 일부다.

## 실습과 관찰

책 루트에서 검증 기록을 읽고 각 명령을 자신의 환경에서 재현한다. 저장소 루트에서는 `python scripts/validate-books.py`를 실행한다. 외부 서비스 검증 결과를 추가했다면 OS·버전·실제 명령·출력·기준 날짜를 기록하고 메타데이터의 검증 범위도 함께 갱신한다.

다음 확장 주제로 업로드 멱등 키·객체 저장소·만료 데이터 정리 중 하나를 골라 실패 시나리오부터 작성한다. 기능을 넓힐 때도 기존 인증과 데이터 불변식을 유지한다.
