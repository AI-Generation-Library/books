# 23장. 실시간 통신과 진행 상황 전달

## 학습 목표

- 폴링·SSE·WebSocket을 통신 방향과 복구 요구에 따라 선택한다.
- 연결 종료·느린 수신자·다중 인스턴스를 처리한다.

## 통신 방식을 고르는 기준

폴링은 일정 간격으로 상태를 조회한다. 단순하고 HTTP 인프라와 잘 맞지만 상태가 바뀌지 않아도 요청이 생긴다. SSE는 서버가 클라이언트에 이벤트를 보내는 단방향 스트림이며, WebSocket은 양방향 메시지 교환에 적합하다. 실시간이라는 이유만으로 가장 복잡한 연결을 먼저 선택할 필요는 없다.

| 방식 | 어울리는 예 | 추가로 설계할 것 |
| --- | --- | --- |
| 폴링 | 수 초 단위 작업 상태 | 주기·백오프·호출량 |
| SSE | 진행 상황·알림 | 재연결·프록시 버퍼링·인증 |
| WebSocket | 대화·협업·게임 | 메시지 계약·하트비트·세션·느린 소비자 |

## SSE의 메시지 형식

```text
event: status
data: {"id":"작업-ID","state":"processing"}

```

이벤트는 빈 줄로 구분된다. 서버는 `Content-Type: text/event-stream`을 보내고 연결을 유지한다. 프록시가 응답을 버퍼링하면 이벤트를 써도 사용자가 나중에 한꺼번에 받을 수 있다. 전체 경로의 버퍼·유휴 기한을 점검한다.

종합 프로젝트의 SSE는 DB의 최신 작업 상태를 250ms 간격으로 조회해 내보내고 30초 또는 종결 상태에서 끝난다. 영속 이벤트 로그를 재생하는 구현이 아니다. 중간 상태를 모두 보장하지 않으며 재연결 시 최신 상태를 다시 읽는다. 사용자에게 필요한 것이 현재 결과인지 모든 이벤트 이력인지 구분한다.

## 인증과 연결 수명

조회와 스트림 모두 동일한 인증·소유권 검사를 거친다. 브라우저 기본 EventSource는 임의 Authorization 헤더를 설정하는 용도로 쓰기 어렵다. 이 예제의 bearer 인증 SSE는 `fetch` 스트리밍 또는 헤더를 지원하는 클라이언트로 읽는다. 토큰을 쿼리에 넣어 우회하지 않는다.

수신자가 연결을 끊으면 타이머와 리스너도 정리한다. 느린 수신자에게 무한히 데이터를 버퍼링하지 않는다. 예제는 `res.write()`가 false면 연결을 끝내고 재연결에 맡기는 단순 정책이다. 이벤트 손실 없이 모두 전달해야 한다면 `drain` 대기와 제한된 큐·영속 커서를 설계해야 한다.

## 재연결과 WebSocket 확장

재연결에는 백오프와 최대 대기 정책을 두고, 연결이 복구되었다고 이전 메시지를 모두 받았다고 가정하지 않는다. SSE의 `id`·Last-Event-ID를 사용하려면 서버도 실제 이벤트 저장과 재생을 구현해야 한다. 필드만 붙이면 이력이 만들어지는 것은 아니다.

WebSocket을 추가한다면 메시지 타입·버전·최대 크기·순서·중복·인증 만료를 정한다. 클라이언트가 보낸 room 이름만 보고 가입시키면 인가 문제가 생긴다. heartbeat와 종료 정책은 반쯤 끊긴 연결을 회수하는 데 필요하다.

여러 인스턴스에서는 한 프로세스의 EventEmitter로 전체 사용자에게 통지할 수 없다. 공유 메시지 시스템이나 DB 상태 조회가 필요하다. Redis Pub/Sub도 영속 이벤트 로그가 아니므로 연결이 끊긴 구간의 복구 요구와 맞는지 확인한다.

## 실습과 관찰

메모리 모드에서 업로드 후 `/jobs/:id/events`를 bearer 헤더와 함께 요청한다. 기본 테스트는 완료 이벤트 형식을 검사하고 타인 작업의 SSE 접근이 404인지 확인한다.

진행률 숫자를 만들려면 실제 전체 작업량과 완료량을 정의해야 한다. 예제는 단계 상태만 제공하며 시간이 지나면 퍼센트를 증가시키는 가짜 진행률을 쓰지 않는다.
