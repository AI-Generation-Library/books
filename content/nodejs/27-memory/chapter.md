# 27장. V8 메모리와 메모리 누수 분석

## 학습 목표

- 힙·외부 메모리·RSS 지표의 차이를 이해한다.
- 보유 참조와 자원 수명을 근거로 누수를 찾는다.

## 메모리 지표의 단위와 범위

`process.memoryUsage()`는 rss·heapTotal·heapUsed·external·arrayBuffers 등의 값을 바이트 단위로 제공한다. JavaScript 힙이 일정하더라도 Buffer·네이티브 라이브러리·메모리 할당 특성 때문에 RSS가 커질 수 있다. 지표를 서로 더하면 중복 계산되는 항목도 있으므로 정의를 확인한다.

V8은 더 이상 접근할 수 없는 객체의 메모리를 회수한다. 함수가 끝났거나 사용자가 로그아웃했다는 업무 의미를 직접 아는 것은 아니다. Map·리스너·타이머·전역 배열이 객체를 계속 참조하면 회수할 수 없다.

```js
const cache = new Map();
function remember(id, value) {
  cache.set(id, value); // 상한·만료·삭제가 없으면 계속 커질 수 있다.
}
```

이 코드는 누수 위험을 설명하는 조각이다. 실제 누수 여부는 키 종류·호출 빈도·수명·예상 최대값에 따라 판단한다. 의도적인 캐시라도 상한이 없으면 장기 운영에서 장애를 일으킬 수 있다.

## GC가 있다는 것과 누수가 없다는 것은 다르다

짧게 생성되고 버려지는 객체와 오래 살아남는 객체는 GC에서 다른 비용을 보인다. 힙을 크게 주면 당장의 메모리 부족을 늦출 수 있지만 근본적인 참조 누수와 GC 지연을 해결하지는 않는다. 프로세스 힙 한도와 컨테이너 전체 메모리 한도도 별개다.

메모리 그래프가 톱니 모양으로 오르내리는 현상 자체는 흔하다. 비슷한 부하를 반복한 뒤 안정 구간의 최저점이 계속 증가하는지, 살아 있는 객체 수와 보유 경로가 무엇인지 본다. RSS만 한 번 측정해 누수라고 결론 내리지 않는다.

## 스냅샷과 할당 프로파일

힙 스냅샷 비교에서는 객체를 붙잡고 있는 보유 경로와 큰 retained size를 확인한다. 예를 들어 요청 객체를 캡처한 이벤트 리스너가 연결 종료 후에도 남아 있을 수 있다. 리스너를 제거하면 해당 요청과 연결된 큰 객체도 회수 가능해질 수 있다.

스냅샷 생성은 시간이 걸리고 메모리를 더 사용하며 프로세스를 멈출 수 있다. 운영 인스턴스 한 개에서 무작정 수집하기보다 복제 환경·트래픽 분리·수집 기한을 고려한다. 파일에는 사용자 데이터와 비밀정보가 들어갈 수 있으므로 공개 PR과 예제 ZIP에 포함하지 않는다.

## 예방하는 설계

메모리 캐시에는 크기와 만료, 리스너와 타이머에는 해제, 큐에는 용량과 기한을 둔다. 스트림을 사용해도 청크를 전역 배열에 계속 쌓으면 전체 읽기와 다르지 않다. Buffer를 문자열로 바꾸거나 복제할 때 중간 메모리도 예상한다.

종합 프로젝트의 메모리 저장소는 수업용이며 사용자를 무한히 받아 운영하도록 만든 저장소가 아니다. 세션·작업·파일의 만료 정리는 별도 확장 과제다. 이런 한계를 밝히고 실제 운영 모드의 보관 정책과 연결한다.

## 실습과 관찰

성능 실험의 memory 출력에서 heapUsed와 rss를 MiB로 바꿔 비교한다. 기본 테스트가 끝난 뒤 프로세스가 정상 종료되는지도 자원 수명의 중요한 단서다.

의도적인 누수를 실험하려면 별도 짧은 스크립트에서 크기와 반복 횟수를 제한한다. 운영 프로세스에서 힙 한도까지 할당하는 방식으로 실험하지 않는다. 이번 집필에서는 힙 스냅샷의 육안 분석을 수행했다고 기록하지 않았다.
