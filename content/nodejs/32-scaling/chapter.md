# 32장. 여러 인스턴스로 확장하기

## 학습 목표

- 프로세스 내부 상태와 공유 상태를 구분한다.
- 프록시·세션·파일·큐·DB의 확장 비용을 함께 본다.

## 인스턴스를 늘리면 무엇이 달라지는가

같은 서버를 두 개 띄워도 메모리 Map과 EventEmitter는 공유되지 않는다. 첫 인스턴스에서 로그인한 세션을 다른 인스턴스가 모르면 인증이 실패한다. 작업 파일이 한 호스트의 디스크에만 있으면 다른 worker가 읽을 수 없다. 단일 프로세스에서 우연히 맞던 가정을 찾아야 한다.

종합 프로젝트의 production 모드는 세션·작업·outbox를 PostgreSQL, 큐를 Redis에 둔다. 그러나 업로드는 Compose 호스트의 공유 볼륨이다. 여러 호스트까지 확장하려면 파일을 객체 저장소 등으로 옮겨야 한다. 모드 이름과 실제 아키텍처 보장을 구분한다.

## 프록시와 TLS

리버스 프록시는 TLS 종료·요청 크기 제한·접속 제어·라우팅을 맡을 수 있다. 애플리케이션은 전달된 클라이언트 주소와 프로토콜 정보를 어디까지 신뢰할지 정한다. 프록시를 통하지 않은 직접 접속이 가능한지도 검토한다.

SSE·WebSocket은 연결이 오래 유지된다. 프록시의 버퍼링·유휴 타임아웃·업그레이드 설정과 애플리케이션의 heartbeat·재연결 정책을 맞춘다. 인스턴스 교체 시 기존 연결이 종료될 수 있으므로 클라이언트 복구가 필요하다. sticky session만으로 이벤트 영속성이나 장애 복구가 생기는 것은 아니다.

## 총 자원 예산

API 인스턴스 4개가 DB 풀 5개씩, worker 3개가 또 5개씩 쓰면 최대 연결 예산은 35개다. 배포 중 이전·새 인스턴스가 공존하면 더 늘 수 있다. DB 최대 연결과 관리용 여유를 고려한다. 큐 소비자 수를 늘리면 DB와 파일 저장소가 다음 병목이 될 수 있다.

인스턴스별 요청 제한기는 전체 서비스의 제한이 아니다. 공유 제한·사용자별 할당량·전역 작업 접수 상한을 설계한다. 장애로 DB가 느려진 상황에서 자동 확장만 계속하면 연결 압력이 더 커질 수도 있다.

## 데이터와 장애 구역

캐시·큐·DB를 같은 호스트에 두면 학습 환경은 단순하지만 한 장애에 함께 영향을 받는다. 가용성 요구가 높으면 관리형 서비스·복제·장애 구역·백업·복구 시간 목표를 함께 검토한다. 복제가 있다고 실수로 지운 데이터가 복구되는 것은 아니므로 백업과 복원 검증이 필요하다.

확장 목표는 인스턴스 수 자체가 아니다. 사용자 요청과 작업 완료의 기한·성공률을 유지하는 것이다. 이벤트 루프 지연·DB 대기·큐 나이·스토리지 지연을 관찰하며 단계별로 확장하고 비용과 복잡성도 기록한다.

## 실습과 관찰

현재 저장 구조를 메모리·PostgreSQL·Redis·로컬 파일로 분류한다. 각 자원을 한 개씩 중단했을 때 어떤 API와 복구 절차가 영향을 받는지 표로 작성한다.

여러 API 인스턴스를 실제로 띄우는 실험은 파일 접근과 포트·프록시 구성을 바꾼 뒤 수행해야 한다. 이 책의 단일 호스트 Compose 실행 여부와 다중 호스트 운영 검증은 구분한다.
