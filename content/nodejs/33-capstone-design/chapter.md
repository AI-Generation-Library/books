# 33장. 요구사항과 아키텍처 설계

## 학습 목표

- 앞선 개념을 파일 처리 서비스의 계약으로 연결한다.
- 성공 시나리오와 실패 시나리오를 함께 설계한다.

## 완성할 서비스

사용자가 가입·로그인하고 UTF-8 텍스트를 업로드하면 비동기로 바이트 수·Unicode 코드포인트 수·줄 수를 계산한다. 작업 ID로 결과를 조회하거나 SSE로 상태를 받는다. 같은 사용자만 자신의 결과에 접근할 수 있고 로그아웃하면 세션이 폐기된다.

텍스트 줄 수는 LF 개수에 마지막 줄의 개행 여부를 반영한다. 빈 파일은 0줄, `a`는 1줄, `a\n`도 1줄이다. CRLF에서는 LF를 줄 구분으로 사용하고 CR도 입력 문자로 센다. 화면상의 그래핌 개수나 단어 수를 세는 서비스는 아니다. 작은 기능도 정확한 계약이 있어야 경계 테스트를 작성할 수 있다.

## 두 실행 모드

메모리 모드는 Node.js와 설치한 패키지만으로 전체 HTTP 흐름을 경험하게 한다. 사용자·세션·작업은 재시작하면 사라진다. 파일은 디스크에 남을 수 있으므로 데이터가 보존되었다고 오해하지 않는다. 학습용 임시 경로를 사용한다.

production 모드는 PostgreSQL·Redis/BullMQ·별도 worker를 조립하는 구현 이름이다. 공개 운영 적합성을 인증하는 표현은 아니다. 영속 저장 경로를 보여 주지만 분산 제한·메일 확인·객체 저장소·백업·고아 파일 정리 등은 확장 항목이다.

```text
클라이언트 → Express API → 세션/작업 저장소
                 └→ 파일 볼륨
작업 접수 → DB outbox → dispatcher → BullMQ → worker
                                             └→ 파일 읽기 → DB 결과
클라이언트 ← GET 또는 SSE ← DB 작업 상태
```

## 불변식과 실패 표

| 불변식 | 검증 지점 |
| --- | --- |
| 타인의 결과는 볼 수 없다 | GET·SSE 소유권 검사 |
| 파일명으로 경로를 바꿀 수 없다 | 서버 UUID와 엄격한 ID 검사 |
| 초과 업로드를 계속 저장하지 않는다 | 실제 바이트 제한과 부분 파일 정리 |
| 큐 전송 실패 시 의도는 남는다 | outbox 삭제 순서 |
| 완료 결과를 실패로 되돌리지 않는다 | 저장소 업데이트 조건 |
| 비밀정보를 오류 응답에 내보내지 않는다 | 공통 오류 처리와 테스트 |

DB 커밋·파일 쓰기·큐 전송 사이의 모든 상태를 완전한 분산 트랜잭션으로 묶지는 않는다. 업로드 크래시의 고아 파일과 오래된 uploading 상태는 운영 정합성 점검 대상이다. 기능 목록뿐 아니라 남은 복구 절차도 설계 문서에 포함한다.

## 구현 순서

먼저 메모리 저장소로 인증·업로드·조회 계약을 고정한다. 다음에 실제 스트리밍과 실패 정리를 연결한다. 작업 처리를 비동기로 분리하고 outbox를 추가한 뒤 DB·큐 어댑터를 붙인다. 마지막에 실제 외부 서비스 통합과 배포 검증을 수행한다. 한 단계의 더블 테스트를 다음 단계의 실행 결과로 바꾸어 기록하지 않는다.

## 실습과 관찰

[프로젝트 안내](../examples/README.md)와 [아키텍처](../examples/ARCHITECTURE.md)를 읽고 `npm test`를 실행한다. 각 불변식이 어느 테스트와 코드에서 유지되는지 대응시킨다.

추가 요구사항으로 업로드 POST 멱등 키를 설계해 보자. 사용자·키·입력 해시·최종 응답·진행 중 상태를 어디에 저장할지 결정하고, 같은 키에 다른 파일을 보내면 어떻게 응답할지도 정한다.
