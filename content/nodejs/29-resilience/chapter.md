# 29장. 실패에 견디는 애플리케이션

## 학습 목표

- 과부하·기한·종료를 하나의 자원 예산으로 설계한다.
- liveness와 readiness의 목적을 구분한다.

## 실패를 예외 경로로만 두지 않는다

외부 API 지연·DB 연결 고갈·디스크 부족·worker 중단은 운영 중 생길 수 있는 상태다. 각 경계에 최대 동시 실행 수·대기 수·작업 기한·재시도 횟수를 둔다. 실패한 요청이 계속 자원을 붙잡고 있으면 정상 요청까지 밀려난다.

제한은 여러 계층에서 필요하다. 인증 시도 제한은 비밀번호 KDF 동시성을 대신하지 않고, 파일 크기 제한은 전체 디스크 사용량을 제한하지 않는다. 종합 프로젝트는 일부 제한을 구현하고 분산 제한·계정별 총량은 운영 확장 항목으로 남겼다.

## 기한과 취소의 전파

사용자 요청에 전체 기한이 있다면 DB·HTTP·파일 처리의 남은 기한도 그 안에 있어야 한다. 하위 호출마다 새 기한을 시작하면 전체 작업이 기대보다 길어질 수 있다. 취소 신호를 전달하되 이미 커밋한 변경은 별도 업무 상태로 확인한다.

대기열은 무한히 늘리지 않는다. 포화 시 429나 503 등 계약한 응답을 빠르게 돌려주고 클라이언트가 재시도 폭주를 만들지 않게 안내한다. 큐 추가가 실패하면 outbox에 남지만, outbox 자체의 적체도 상한과 경보가 필요하다.

## 회로 차단과 재시도 예산

지속 실패하는 외부 서비스에 매번 끝까지 대기하면 내부 자원도 소모된다. 일정 실패 조건에서 호출을 줄이고 제한적으로 회복을 확인하는 circuit breaker를 검토할 수 있다. 그러나 임계값·반개방·회복·메트릭을 설계하지 않고 라이브러리만 추가하면 새로운 실패 상태를 만들 수 있다.

여러 계층이 각각 세 번 재시도하면 실제 호출은 곱으로 늘어날 수 있다. 재시도 책임을 정하고 전체 예산을 제한한다. 사용자 요청과 백그라운드 작업은 허용 지연·내구성 요구가 다르므로 같은 정책을 강제로 쓰지 않는다.

## 헬스 체크의 두 질문

`/health/live`는 프로세스가 살아 응답할 수 있는지, `/health/ready`는 새 트래픽을 받을 준비가 되었는지를 묻는다. 외부 DB가 잠깐 끊겼다는 이유로 liveness까지 실패시키면 재시작 폭주가 생길 수 있다. 종합 프로젝트는 readiness에서 DB와 큐를 확인하고 liveness는 단순하게 유지한다.

준비 상태가 200이라는 사실도 모든 업무 성공을 증명하지 않는다. 실제 업로드·분석·조회 흐름은 별도 smoke 검증으로 확인한다. 헬스 체크의 쿼리와 빈도 자체가 DB 부하가 되지 않게 한다.

## 안전한 종료 순서

종료 신호 수신 → readiness 해제 → 신규 요청 접수 중단 → 진행 중 요청 대기 → dispatcher 중지 → 큐·DB 종료 순서로 소유 자원을 정리한다. 장시간 SSE나 업로드는 종료 기한에 포함한다. worker는 새 작업을 멈추고 진행 중 작업 완료를 기다린다.

모든 정리가 무한히 기다리지 않도록 최종 기한을 둔다. 기한을 넘겨 강제 종료하면 진행 중 작업이 다시 실행될 수 있음을 설계에 포함한다. `uncaughtException`을 잡고 아무 일 없던 것처럼 계속 운영하는 방식은 손상된 상태를 숨길 수 있다. 진단 자료를 남기고 재시작 가능한 구조를 만든다.

## 실습과 관찰

`src/main.mjs`의 종료 함수와 `src/worker.mjs`를 비교한다. HTTP 테스트는 drain 이후 readiness가 503이고 liveness는 200인지를 확인한다.

실제 SIGTERM 전달과 배포 시 트래픽 이동은 OS·컨테이너·프록시 환경에서 별도로 시험해야 한다. 이번 Windows 로컬 테스트만으로 Linux 운영 종료를 검증했다고 기록하지 않는다.
