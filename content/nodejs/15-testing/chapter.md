# 15장. 테스트 가능한 서버 만들기

## 학습 목표

- 성공·실패·경계 조건을 관찰 가능한 결과로 검증한다.
- 단위·HTTP 통합·외부 서비스 통합 검증을 구분한다.

## 무엇을 보장하려는 테스트인가

단위 테스트는 작은 규칙을 빠르게 확인한다. HTTP 통합 테스트는 실제 소켓·라우팅·인증·직렬화를 연결한다. PostgreSQL·Redis 통합 테스트는 그 자원의 실제 동작을 확인한다. 메모리 Map이 SQL의 잠금·제약·격리 수준을 흉내 낼 수는 없다.

예제의 기본 테스트는 실제 로컬 HTTP 요청을 사용하지만 저장소와 큐는 메모리 구현이다. 별도 `integration` 테스트는 실제 PostgreSQL·Redis에 명시적으로 연결한다. 외부 서비스가 없으면 건너뛰며, 이 skip을 실행 성공으로 기록하지 않는다.

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { mapLimit } from './src/map-limit.mjs';
test('결과는 입력 순서다', async () => {
  assert.deepEqual(await mapLimit([2, 1], 2, async n => n * 2), [4, 2]);
});
```

## 구현을 베끼는 테스트 대신 실패 조건 찾기

문자열 분석 테스트는 정상 한글뿐 아니라 한 바이트씩 나뉜 입력, 빈 파일, 마지막 개행 유무, 잘못된 UTF-8을 확인한다. 인증 테스트는 로그인 성공뿐 아니라 타인 작업 조회와 로그아웃 후 접근 거부를 확인한다. 내부 함수를 몇 번 호출했는지보다 사용자에게 보이는 결과와 데이터 불변식을 우선한다.

동시 실행 제한은 최종 결과가 맞는지만 검사하면 누락될 수 있다. 실행 중 개수를 측정해 최대값이 설정을 넘지 않는지 검증한다. 완료 작업이 실패 상태로 되돌아가지 않는지도 상태 전이의 중요한 조건이다.

## 자원 수명과 테스트 독립성

포트 0으로 서버를 열고 `listening`을 기다린다. 테스트가 만든 임시 디렉터리만 정리한다. 성공 여부와 관계없이 `t.after`에서 dispatcher·소켓·작업·파일을 정리한다. 열려 있는 타이머와 연결 때문에 테스트 프로세스가 끝나지 않는다면 강제 종료로 숨기지 말고 소유자를 찾는다.

임의의 긴 `sleep`은 느리고 불안정하다. 조건이 만족될 때까지 제한된 기한 내에서 확인하거나 이벤트를 기다린다. 기한이 지난 경우에는 마지막 상태를 실패 메시지에 남긴다. 운영 환경의 지연 값을 테스트의 정확한 상수로 고정하지 않는다.

## 테스트 더블의 한계

외부 API 실패나 DB 장애를 의도적으로 재현하려면 더블이 유용하다. 예제는 `repo.ping`이 실패하도록 바꿔 내부 오류가 응답에 새지 않는지 검사한다. 그러나 더블이 반환한 SQL 결과만 보고 실제 쿼리가 맞다고 결론 내리면 안 된다.

코드 커버리지는 실행한 경로를 보여 주는 보조 지표다. 중요한 경계를 검사했는지, 잘못된 코드가 들어왔을 때 테스트가 실제로 실패하는지가 더 중요하다. 테스트 개수만으로 완성도를 평가하지 않는다.

## 실습과 관찰

`npm test`와 `npm run typecheck`를 실행한다. 테스트 이름과 실제 검증 범위를 연결한다. `test/http.test.mjs`의 다른 사용자 접근 테스트에서 소유권 검사를 제거하면 실패하는지 확인하고 즉시 복구한다.

외부 서비스 테스트는 전용 DB에서만 실행한다. 방법은 [예제 안내](../examples/README.md)에 있으며, 이번 집필 환경에서 실제 수행한 범위는 [검증 기록](../appendices/verification.md)이 기준이다.
