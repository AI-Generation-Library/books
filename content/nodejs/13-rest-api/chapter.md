# 13장. 일관된 REST API 설계

## 학습 목표

- 리소스·상태 코드·입력 검증·오류 형식을 일관되게 정한다.
- 페이지네이션과 멱등성의 보장 범위를 설명한다.

## API는 구현보다 먼저 정하는 계약

파일 처리 서비스의 핵심 리소스는 작업이다. `POST /jobs`는 작업을 만들고, `GET /jobs/:id`는 상태를 읽는다. 내부 함수 이름을 그대로 URL로 만드는 대신 사용자가 다루는 자원과 상태 전이를 표현한다.

| 요청 | 정상 결과 | 주요 실패 |
| --- | --- | --- |
| POST /auth/register | 201, 사용자 ID | 400 입력 오류, 409 중복 |
| POST /auth/login | 200, 세션 토큰 | 401 인증 실패, 429 제한 |
| POST /jobs | 202, 작업 ID·Location | 401, 413 크기 초과, 415 형식 |
| GET /jobs/:id | 200, 상태·결과 | 400 잘못된 ID, 404 미존재·권한 없음 |
| POST /auth/logout | 204 | 401 |

202는 작업을 접수했다는 뜻이지 분석 완료가 아니다. 클라이언트는 반환 ID로 완료 여부를 확인한다. 응답의 `state`가 `queued`여도 빠른 워커가 직후 완료할 수 있으므로 다시 조회한 상태가 더 진행되어 있는 것은 정상이다.

## 검증할 위치와 값

네트워크 입력은 신뢰하지 않는다. JSON 문법이 맞다는 것과 업무 입력이 맞다는 것은 다르다. 필수 값·타입·길이·허용 범위·알 수 없는 필드 정책을 정한다. 객체를 DB에 그대로 넘기는 방식은 수정하면 안 되는 소유자·권한 필드를 변경하게 만들 수 있다.

종합 프로젝트는 이메일·비밀번호·UUID·Content-Type·실제 업로드 바이트를 각각 검증한다. 사용자 ID는 요청 본문이 아니라 인증 세션에서 가져온다. 검증 도구를 사용해도 인증과 자원 소유권 검사까지 대신해 주지는 않는다.

## 오류도 계약이다

오류는 `error.code`, 안전한 설명, `requestId` 형태로 반환한다. 클라이언트가 자연어 메시지 전체를 파싱하지 않게 코드를 둔다. 오류 원인을 숨기겠다고 모든 응답을 200으로 보내면 재시도·알림·모니터링이 어려워진다.

400·401·403·404·409·413·415·429·500·503은 서로 다른 상황이다. 다만 민감한 자원의 존재를 드러내지 않기 위해 권한 없는 접근을 404로 통일하는 선택도 있다. 클라이언트 계약과 운영 지표에 그 선택을 기록한다.

## 페이지네이션과 재시도

목록에 offset 페이지를 쓰면 구현이 쉽지만 데이터가 삽입·삭제되는 동안 중복과 누락이 생길 수 있다. 커서는 `(created_at, id)` 같은 안정적인 정렬 키를 기준으로 이어 읽게 한다. 커서 자체도 입력 검증 대상이며 페이지 크기 상한을 둔다.

네트워크 응답을 못 받았다고 서버가 변경을 수행하지 않았다는 뜻은 아니다. 결제·작업 생성의 자동 재시도에는 요청 키와 DB 유니크 제약 등을 이용한 멱등성 설계가 필요하다. 종합 프로젝트의 **워커 재실행**은 멱등적으로 처리하지만 **업로드 POST 재전송**까지 같은 작업으로 묶지는 않는다. 필요하면 사용자·요청 키·본문 해시·응답을 저장하는 계층을 추가한다.

## 실습과 관찰

`npm run smoke`는 201 → 200 → 202 → 상태 조회 → 204 흐름을 검사한다. 테스트에서 413·415·401·404 응답도 확인한다. 성공 예제만 문서화하면 클라이언트가 무엇을 고쳐야 하는지 알 수 없으므로 입력 오류 예시도 함께 작성한다.

파일 처리 API 명세는 [프로젝트 설계](../examples/ARCHITECTURE.md)에 있다. API 계약을 바꾸면 테스트와 설명을 같은 변경에서 갱신한다.
