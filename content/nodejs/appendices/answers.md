# 확인 문제 해설

각 해설은 답의 핵심이다. 자신의 코드와 실행 결과로 설명을 보완한다.

## 장 01

**문제:** DB 대기는 거의 없는데 CPU가 꽉 차고 모든 요청이 느려졌다. async 함수를 더 많이 호출하면 해결되는가?

해결되지 않는다. 같은 스레드에서 실행되는 계산량을 먼저 프로파일링하고 줄이거나 분리한다. 동시 호출을 늘리면 대기와 메모리 사용이 더 커질 수 있다.

[본문으로](../01-runtime/chapter.md)

## 장 02

**문제:** IDE에서는 실행되지만 터미널에서는 설정 파일을 찾지 못한다. 가장 먼저 비교할 값은 무엇인가?

Node.js 실행 파일과 버전, process.cwd(), 명령 인자, 환경 변수를 비교한다. 파일 기준 경로와 작업 디렉터리 기준 경로를 혼동했는지 확인한다.

[본문으로](../02-environment/chapter.md)

## 장 03

**문제:** 전역 배열에 요청 데이터를 넣고 응답 후 함수가 끝났다. 그 데이터는 자동으로 제거되는가?

아니다. 전역 배열이 참조하는 동안 데이터가 남는다. 수명과 용량 제한, 삭제 시점이 필요하며 개인정보를 요청 간 공유하지 않아야 한다.

[본문으로](../03-javascript/chapter.md)

## 장 04

**문제:** package.json에 모든 직접 의존성을 고정했으므로 잠금 파일을 삭제해도 재현 가능한가?

아니다. 전이 의존성의 해석 결과까지 같아야 한다. 잠금 파일을 유지하고 npm ci로 설치하며 런타임과 OS도 기록해야 한다.

[본문으로](../04-npm-project/chapter.md)

## 장 05

**문제:** 테스트를 위해 서비스 모듈을 import했는데 실제 DB에 연결된다. 모듈 구조를 어떻게 바꾸는가?

최상위 연결 생성 부수 효과를 제거하고 연결이나 저장소를 인자로 받게 한다. 실제 자원 생성과 서버 시작은 실행 진입점에 둔다.

[본문으로](../05-modules/chapter.md)

## 장 06

**문제:** Promise.all이 첫 오류로 거부되었다. 다른 요청도 모두 중단되었다고 가정해도 되는가?

아니다. 시작된 작업은 계속 실행될 수 있다. 취소 신호를 전달하고 지원 여부를 확인하며, 외부 부수 효과에는 멱등성이나 보상 처리가 필요하다.

[본문으로](../06-async/chapter.md)

## 장 07

**문제:** await Promise.resolve()를 긴 루프 안에 넣었으므로 HTTP 요청도 충분히 처리할 수 있다는 주장이 맞는가?

일반적으로 보장할 수 없다. 마이크로태스크만 이어질 수 있다. setImmediate를 통한 양보나 Worker 분리를 검토하고 실제 이벤트 루프 지연을 측정한다.

[본문으로](../07-event-loop/chapter.md)

## 장 08

**문제:** 파일이 없다는 것을 확인했으니 다음 쓰기에서 기존 파일을 덮어쓸 수 없다고 말할 수 있는가?

아니다. 확인과 쓰기 사이에 다른 작업이 파일을 만들 수 있다. 배타적 생성 플래그를 사용하고 실패를 처리한다.

[본문으로](../08-filesystem/chapter.md)

## 장 09

**문제:** 파일의 characters가 화면에서 보이는 글자 수와 달랐다. 반드시 버그인가?

정의에 따라 다르다. 코드 단위·코드포인트·그래핌·바이트는 다른 단위다. API 계약에 단위를 명시하고 필요하면 Intl.Segmenter 등으로 그래핌을 계산한다.

[본문으로](../09-buffer-events/chapter.md)

## 장 10

**문제:** write()가 false를 반환해 같은 청크를 다시 write했다. 어떤 문제가 생길 수 있는가?

해당 청크는 이미 버퍼에 받아들여졌다. 다시 쓰면 중복될 수 있다. drain 이후 다음 청크를 보내거나 pipeline으로 흐름 제어를 맡긴다.

[본문으로](../10-streams/chapter.md)

## 장 11

**문제:** 응답을 일부 스트리밍한 뒤 오류가 났다. 500 JSON을 새로 보내도 되는가?

이미 헤더와 일부 본문을 보냈다면 응답 형식을 바꿀 수 없다. 연결을 정리하고 로그·추적 정보로 원인을 남겨야 한다. 수신자는 부분 응답 실패를 처리해야 한다.

[본문으로](../11-http/chapter.md)

## 장 12

**문제:** async 함수 안에서 시작한 Promise를 반환하지 않았다. 그 Promise의 실패를 Express 5가 항상 처리하는가?

아니다. 핸들러가 반환하거나 await하는 Promise와 연결해야 한다. 별도 백그라운드 작업은 자체 실패·종료 정책이 필요하다.

[본문으로](../12-express/chapter.md)

## 장 13

**문제:** 업로드 POST 응답을 잃어버려 재전송했다. 워커가 멱등적이므로 작업 ID도 하나만 생기는가?

아니다. 업로드 요청 중복 제거와 기존 작업의 중복 실행 처리는 별개다. 요청 키를 사용한 별도 접수 멱등성 설계가 필요하다.

[본문으로](../13-rest-api/chapter.md)

## 장 14

**문제:** JSON을 읽은 뒤 as Job을 붙였으므로 state가 올바르다고 믿을 수 있는가?

아니다. 타입 단언은 런타임 검사 코드를 만들지 않는다. 외부 입력은 실제 값의 타입·허용 상태·필수 필드를 검사해야 한다.

[본문으로](../14-typescript-architecture/chapter.md)

## 장 15

**문제:** 메모리 모드 HTTP 테스트가 통과했다. DB 트랜잭션의 동시성도 검증되었다고 기록해도 되는가?

안 된다. HTTP 경계와 메모리 구현을 검증한 것이다. DB 제약·격리·연결 실패는 실제 PostgreSQL을 사용한 별도 검증이 필요하다.

[본문으로](../15-testing/chapter.md)

## 장 16

**문제:** 이메일 중복을 SELECT로 검사한 뒤 INSERT했다. UNIQUE 제약이 없어도 안전한가?

동시 요청에서는 안전하지 않다. DB 유니크 제약을 두고 충돌을 처리한다. 사전 조회는 사용자 경험을 돕지만 최종 보장을 대신하지 않는다.

[본문으로](../16-postgresql/chapter.md)

## 장 17

**문제:** 트랜잭션 내부에서 Redis에 메시지를 보냈다. 나중에 DB가 롤백되면 Redis 메시지도 사라지는가?

사라지지 않는다. 서로 다른 자원이다. outbox 등으로 전달 의도를 DB에 저장하고 재전송과 소비자 멱등성을 설계한다.

[본문으로](../17-transactions/chapter.md)

## 장 18

**문제:** JWT를 쓰지 않고 DB 세션을 쓰면 인증 설계가 오래된 방식인가?

아니다. 요구사항에 따른 선택이다. DB 세션은 즉시 폐기가 쉽고 저장소 조회가 필요하다. JWT는 검증 분산이 쉬울 수 있지만 폐기·키 관리·클레임 검증이 필요하다.

[본문으로](../18-authentication/chapter.md)

## 장 19

**문제:** CORS를 허용하지 않았으니 외부 스크립트와 다른 서버는 API에 요청할 수 없는가?

아니다. CORS는 브라우저의 응답 접근 정책이다. 비브라우저 클라이언트와 서버 간 호출을 막지 않는다. 인증·인가·네트워크 정책은 별도로 필요하다.

[본문으로](../19-web-security/chapter.md)

## 장 20

**문제:** TTL을 10초로 설정했으니 변경 직후에도 항상 최신 값을 읽는가?

아니다. TTL은 낡은 데이터가 남는 시간을 제한하는 도구다. 즉시 일관성이 필요한 값은 원본 조회나 별도 일관성 프로토콜이 필요하다.

[본문으로](../20-redis-cache/chapter.md)

## 장 21

**문제:** 타임아웃 예외를 받았으므로 상대 서버의 작업도 취소되었다고 판단해도 되는가?

안 된다. 클라이언트 대기나 연결이 끝나도 상대의 변경은 완료될 수 있다. 결과 조회·멱등 키·업무 상태 확인이 필요하다.

[본문으로](../21-http-client/chapter.md)

## 장 22

**문제:** BullMQ jobId를 썼으므로 완료 후 몇 달이 지나도 같은 업무가 다시 실행될 수 없는가?

그렇지 않다. 큐 보관 정책과 업무 중복 방지는 다르다. 업무 저장소의 상태·유니크 키와 소비자의 멱등성을 유지해야 한다.

[본문으로](../22-job-queue/chapter.md)

## 장 23

**문제:** SSE 응답에 id만 붙이면 서버 재시작 후 놓친 이벤트도 복구되는가?

아니다. 서버가 이벤트를 영속 저장하고 커서 이후 이력을 재생해야 한다. 현재 상태만 조회하는 서비스는 그 한계를 계약에 명시해야 한다.

아니다. 사용자별 총량·파일 수·보관 기간·동시 업로드·전역 디스크 여유를 함께 제한하고 정리해야 한다.

아니다. 쿼리·연결 풀·DB 용량·네트워크 지연을 먼저 측정한다. 비동기 I/O를 Worker로 옮긴다고 DB 자체가 빨라지지 않으며 연결 폭주가 생길 수 있다.

**문제:** 평균 응답 시간만 개선되었으므로 성능 개선이 완료되었다고 판단할 수 있는가?

아니다. p95/p99·오류율·처리량·자원 사용과 측정 조건을 함께 봐야 한다. 일부 사용자에게 지연과 실패가 집중될 수 있다.
