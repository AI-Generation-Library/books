# 31장. CI/CD와 안전한 변경 배포

## 학습 목표

- 의존성·테스트·콘텐츠 검사를 반복 가능한 명령으로 연결한다.
- 코드와 DB 변경을 이전 버전과 공존할 수 있게 배포한다.

## 한 번의 성공을 반복 가능한 검사로 바꾸기

CI는 깨끗한 체크아웃에서 선언된 런타임과 잠금 파일로 설치하고 검사한다. 개발자의 전역 패키지와 오래된 `node_modules`가 오류를 숨기지 않게 한다. 검사 명령은 프로젝트가 소유하고, CI 설정은 그 명령을 호출하는 얇은 계층으로 유지한다.

```sh
npm ci --ignore-scripts
npm test
npm run typecheck
```

책 저장소에서는 여기에 루트의 `python scripts/validate-books.py`가 필요하다. 메타데이터 검사는 원고 경로와 출처를 확인하지만 예제 코드 실행이나 기술적 정확성을 대신 검증하지 않는다. 각 검사가 무엇을 보장하는지 PR에 기록한다.

## 외부 서비스 테스트를 CI에 넣기

실제 PostgreSQL·Redis를 사용하는 job은 전용 서비스와 초기화 단계를 둔다. 통합 테스트가 skip되었는데 성공 배지 하나만 보고 검증 완료로 오해하지 않도록, 통합 job에서는 필수 환경 변수를 검사하고 테스트 실행을 강제한다.

서비스 버전·헬스 체크·연결 포트·초기화·테스트 데이터 정리·기한을 명시한다. 운영 DB 접속 비밀을 테스트에 재사용하지 않는다. PR에서 신뢰할 수 없는 코드가 실행되는 상황의 토큰 권한과 비밀 제공 조건도 검토한다.

이 책의 예제는 CI에 옮길 검사 명령과 외부 서비스 테스트 파일을 제공한다. 저장소 전체의 배포 정책을 바꾸는 워크플로를 책 기여 PR에 추가하지는 않는다. 콘텐츠 저장소의 기존 검사는 그대로 이용한다.

## 배포 산출물과 권한

검사한 소스로 이미지를 한 번 만들고 동일 산출물을 환경별로 승격하면 재현성을 높일 수 있다. 환경마다 소스를 다시 빌드하면 의존성·기본 이미지 변경이 섞일 수 있다. 이미지 식별자와 소스 커밋·검사 기록을 연결한다.

배포 토큰은 필요한 저장소·레지스트리·환경 권한만 갖게 한다. 비밀을 Dockerfile의 ARG나 소스에 넣어 이미지 레이어에 남기지 않는다. 패키지·이미지 취약점 검사는 운영에 미치는 경로와 함께 평가하고 갱신 후 회귀 검증을 수행한다.

## DB 변경과 롤백

애플리케이션 v1과 v2가 잠시 동시에 실행될 수 있다. 컬럼 이름을 즉시 바꾸거나 제거하면 이전 인스턴스가 실패할 수 있다. 새 컬럼 추가 → 양쪽 호환 쓰기·읽기 → 데이터 이행 → 이전 코드 종료 확인 → 이전 컬럼 제거처럼 단계를 나누는 expand-contract 전략을 검토한다.

코드 이미지를 되돌렸다고 DB 데이터 변경도 되돌아가지는 않는다. 파괴적 변경과 대용량 백필은 별도 계획·기한·관찰·복구 절차를 갖춘다. 새 기능을 일부 사용자에게 점진적으로 적용할 때도 성공 지표와 중단 기준을 먼저 정한다.

## 실습과 관찰

깨끗한 설치 후 기본 테스트와 타입 검사를 수행하고 버전·결과를 기록한다. 외부 서비스 통합 명령은 `examples/README.md`를 따른다.

이번 책 PR의 콘텐츠 CI 결과는 GitHub에서 확인한다. CI가 검사하지 않은 컨테이너 배포·실제 클라우드·사람 검수를 완료로 표시하지 않는다.
