> PART 6. 통합 실습과 설계

## 도입: 정의는 외웠는데 선택 이유를 묻자 막힌다

“DI는 의존성 주입입니다”는 시작일 뿐이다. 왜 생성자로 받았는지, 인터페이스가 필요한지, 어떤 테스트가 쉬워졌는지까지 설명하면 설계 판단이 된다. 이 장은 짧은 정의 → 구체적인 실패 사례 → 선택한 경계 → 검증 결과 순서로 답하는 연습이다.

## 26.1 Spring의 네 개념을 한 사례로 설명하기

**질문: POJO·IoC/DI·AOP·PSA가 어떻게 연결되는가?** 예약 규칙은 일반 Java 객체로 표현하고 저장소를 생성자로 주입한다. 호출자는 서비스 프록시를 통해 트랜잭션 경계를 적용받고, 트랜잭션 매니저가 데이터 접근 기술에 맞는 자원을 처리한다. Boot는 클래스와 설정 조건에 맞춰 기반 구성을 제공한다.

추가 질문으로 “그래서 모든 객체를 빈으로 만들었는가?”가 나오면 요청 DTO와 계산 결과는 작업별 데이터이고 공유 서비스와 수명이 다르다고 설명한다. singleton과 스레드 안전성도 분리한다.

## 26.2 Transactional이 동작하지 않을 때

**질문: 어노테이션이 있는데 rollback이 안 된다면?** 빈이 관리 객체인지, 호출이 프록시를 통과했는지, 자기 호출·private·final 제약이 있는지, 어떤 예외가 밖으로 나갔는지, 자원이 같은 매니저에 참여했는지 순서대로 확인한다.

“모든 예외는 rollback”이라고 말하지 않는다. 기본 checked exception 정책과 rollbackFor를 설명하고, catch가 경계 안인지 다른 REQUIRED 프록시 밖인지 구분한다. TransactionTests의 최종 audit_log 행 수를 증거로 제시할 수 있다.

## 26.3 마지막 재고 하나를 보호하는 설계

**질문: 동시에 두 예약이 들어오면?** 단순 조회 후 감소는 경쟁이 생긴다. 예제는 재고 조건과 감소를 같은 UPDATE에 넣고 영향받은 행 수로 판단한다. 예약·재고·Outbox를 한 트랜잭션으로 묶으며 DB CHECK와 UNIQUE로 최종 무결성을 보강한다.

복수 행 불변식이면 조건부 한 문장만으로 충분한지 검토하고 락·버전·SERIALIZABLE 등의 대가를 평가한다. “synchronized로 해결”은 한 JVM 범위만 보호하므로 여러 서버에서는 별도 대안이 필요하다.

## 26.4 실패한 주문의 감사 로그

**질문: 주문이 실패해도 감사 로그를 남기려면?** 감사 사실이 주문 성공과 독립적인지 먼저 정의한다. 별도 빈의 REQUIRES_NEW로 독립 commit할 수 있지만 추가 연결과 잠금 대기 위험이 있다. 안쪽이 아직 commit되지 않은 바깥 주문 행에 의존하지 않도록 설계한다.

NESTED는 savepoint 기반 부분 rollback이며 바깥 최종 rollback에서 함께 취소된다는 점을 구분한다. Outbox는 주문 성공과 함께 남아야 할 사건을 기록하는 데 사용하므로 “실패 감사”와 동일 목적이 아니다.

## 26.5 API가 느릴 때의 조사

**질문: 응답 시간이 갑자기 늘면?** 평균만 보지 않고 p95·p99·실패율·처리량을 확인한다. trace로 풀 획득·SQL·외부 HTTP·직렬화 시간을 나누고 DB 락·스레드·GC 신호를 연결한다. 풀을 무조건 늘리거나 WebFlux로 옮기기 전에 병목을 증명한다.

기능 동시성 테스트와 부하 테스트를 구분한다. 이 책의 “12건 중 5건 성공”은 초과 판매 방지 검증이지 운영 초당 처리량 수치가 아니다.

## 26.6 결제 timeout과 재시도

**질문: 결제 서버가 timeout이면 재시도하는가?** 결과 불명일 수 있으므로 외부 멱등 키와 상태 조회 계약을 확인한다. 새 키로 다시 결제하지 않는다. 제한된 재시도와 새 트랜잭션, 후속 복구 상태를 설계하며 HTTP timeout이 DB rollback을 뜻하지 않는다고 설명한다.

여러 서비스의 일관성을 묻는다면 로컬 트랜잭션, Outbox의 at-least-once, 멱등 소비, Saga 보상의 실패 가능성을 단계별로 이야기한다. 모든 경계에서 exactly-once라고 과장하지 않는다.

## 26.7 MVC·가상 스레드·WebFlux 선택

**질문: 가장 빠른 것은 무엇인가?** 업무 특성·드라이버·대기 비율·팀 경험에 따라 다르다. 기존 JDBC·JPA 중심이면 MVC의 단순성이 장점일 수 있고, 가상 스레드는 많은 대기 작업의 비용을 줄이는 선택이며, 비차단 전체 경로와 스트리밍이면 WebFlux를 검토한다. 어느 선택도 DB 용량과 외부 API 한도를 없애지 않는다.

## 26.8 설계 리뷰용 결정 기록

| 항목 | 예약 API의 현재 선택 | 확장 시 다시 물을 질문 |
| --- | --- | --- |
| 조립 | 생성자 DI | 인터페이스로 바뀌는 실제 축은? |
| 데이터 접근 | JdbcTemplate | JPA 변경 추적이 필요한가? |
| 업무 원자성 | 서비스 트랜잭션 | 외부 부수효과를 어떻게 분리하는가? |
| 재고 동시성 | 조건부 UPDATE | 여러 SKU·상태 전이에도 충분한가? |
| 중복 방지 | 사용자+키 UNIQUE | 보관 기간·재기동·키 재사용은? |
| 이벤트 | 같은 DB의 Outbox 기록 | 전달·중복·순서·복구는? |
| 인증 | 학습용 Basic·CSRF | 실제 IdP·테넌트·TLS는? |
| 저장 | H2 메모리 | 목표 DB·백업·RPO/RTO는? |

결정 기록에는 선택, 이유, 대안, 아직 검증하지 않은 가정을 적는다. 한 번 선택했다고 영구 정답으로 만들지 않는다. 요구나 측정 결과가 바뀌면 결정도 바뀔 수 있다.

## 종합 확인 문제와 해설

**문제.** 예약은 DB에 있는데 고객은 500을 받았다. 곧 같은 키의 재시도가 왔다. 알림은 두 번 수신됐다. 무엇을 조사할 것인가?

**해설.** DB commit과 응답 실패 시점을 분리한다. 멱등 키로 기존 결과를 재사용했는지, 재시도마다 새 키를 만들지 않았는지 확인한다. Outbox 행이 한 개인지, 발행 후 완료 표시 전에 장애가 났는지, 소비자의 event_id 중복 방지가 같은 업무 트랜잭션에 들어갔는지 조사한다. 응답 실패와 중복 알림을 단일 rollback 버그로 단정하지 않는다.

**마지막 연습.** 3·5·12~15장을 다시 읽은 뒤 첨부 테스트 이름을 보지 않고 DI, 자기 호출, 롤백, 전파, 재고 경쟁에 대한 검증을 한 개씩 설계한다. 테스트가 실행 없이도 결과를 단정하는 암기가 아니라 자신의 가정을 깨뜨릴 수 있는 실험인지 점검한다.
