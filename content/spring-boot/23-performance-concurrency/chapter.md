> PART 5. 검증과 운영

## 도입: 스레드를 늘렸더니 p99가 더 나빠졌다

요청 스레드 수를 늘리자 더 많은 요청이 DB 풀 앞에서 기다린다. 처리량은 비슷한데 메모리와 꼬리 지연이 늘었다. 동시 실행 수, 대기열 길이, 처리 능력을 구분하지 않으면 설정 숫자를 늘리는 것이 문제를 키울 수 있다.

## 23.1 측정 단어를 정의한다

**Throughput**은 단위 시간에 완료한 작업 수, **latency**는 개별 요청에 걸린 시간이다. **Concurrency**는 동시에 진행 중인 작업 수다. 요청 속도가 같은데 처리 시간이 길어지면 진행 중인 작업이 늘어나는 경향이 있다.

안정적인 시스템의 평균값을 다루는 Little의 법칙은 `L = λ × W`다. 예를 들어 초당 100건이 평균 0.2초 동안 시스템에 머무르면 평균 진행 중 작업은 약 20개다. 이는 평균 관계를 설명하는 예시이며 burst·p99·재시도·무한 큐까지 해결하는 용량 공식이 아니다.

## 23.2 요청 시간을 분해한다

```text
전체 지연 = 입구 대기 + 스레드 대기 + DB 풀 획득
          + SQL/락 대기 + 외부 API + 직렬화 + 전송
```

구간이 겹치는 병렬 실행에서는 단순 합산이 맞지 않을 수 있다. 실제 critical path를 trace로 확인한다. CPU가 낮으면 I/O·잠금 대기를, CPU가 높으면 직렬화·계산·GC·루프 등을 가설로 세운다. 측정 전에 원인을 확정하지 않는다.

## 23.3 플랫폼 스레드와 가상 스레드

플랫폼 스레드는 OS 스레드와 연결된 실행 자원이고, 가상 스레드는 JVM이 더 가볍게 다수의 대기 작업을 표현할 수 있게 하는 실행 모델이다. I/O 대기가 많은 동기 코드를 단순하게 유지하는 데 도움이 될 수 있다. CPU 계산 자체를 더 빠르게 하거나 DB 연결 한도를 늘려주지는 않는다.

Boot에서 지원하는 가상 스레드 설정을 활성화하더라도 선택한 JDK와 라이브러리의 동작을 검증한다. Java 21과 이후 JDK는 pinning 관련 제약·개선이 다를 수 있으므로 한 버전의 설명을 영구 규칙으로 외우지 않는다. 가상 스레드 수가 늘면 외부 시스템에 더 많은 요청을 보낼 수 있으므로 별도 동시성 제한이 필요하다.

## 23.4 WebFlux는 언제 고려하는가

WebFlux는 반응형·비차단 웹 스택이다. Reactor의 `Mono`는 0~1개, `Flux`는 0~N개 데이터 흐름을 표현한다. 반환 타입을 Mono로 감쌌다고 내부 JDBC 호출이 비차단으로 바뀌지는 않는다. 이벤트 루프에서 블로킹 호출을 수행하면 여러 요청의 진행을 막을 수 있다.

끝까지 비차단인 드라이버·외부 호출과 스트리밍 요구가 있다면 선택 가치가 있다. 기존 JPA·JDBC 중심 서비스는 MVC와 적절한 스레드·풀 관리가 더 단순할 수 있다. 블로킹 작업을 다른 실행기로 옮기는 선택도 가능하지만 큐·스케줄링·취소 복잡성이 추가된다.

반응형 트랜잭션은 Reactor Context와 publisher 실행 흐름을 기준으로 참여한다. 일반 스레드 로컬 트랜잭션을 임의의 subscribe 호출과 섞지 않는다. 구독·취소가 실제 부수효과와 자원 정리에 어떤 영향을 주는지 확인한다. 이 책의 통합 예제는 MVC·JDBC이며 WebFlux 성능 비교를 실행하지 않았다.

## 23.5 부하 실험을 설계한다

단순 health endpoint는 예약·DB·보안 경로의 처리량을 대변하지 않는다. 데이터 크기·캐시 상태·동시 사용자·요청 비율·오류 비율을 실제 시나리오에 맞춘다. JVM warm-up과 테스트 시간, 하드웨어·JDK·풀 크기를 함께 기록한다.

고정 동시 사용자 방식은 응답이 느려지면 새 요청 발행도 줄어 시스템 과부하를 덜 드러낼 수 있다. 고정 도착률 방식은 실제 도착 부하를 더 명확히 다루지만 발생기 자체의 한도와 누락 요청도 봐야 한다. p95·p99, 성공률, 실제 발행률, 완료률, DB 연결 대기와 GC를 함께 저장한다.

## 23.6 최적화 순서

불필요한 쿼리·N+1·긴 트랜잭션·외부 호출의 과도한 재시도부터 제거한다. 그다음 캐시·배치·인덱스·풀 크기를 증거에 따라 조정한다. 비동기나 가상 스레드 도입은 문제 위치와 팀의 운영 능력에 맞춰 결정한다.

## 실습: 기능 테스트와 성능 테스트를 나눈다

첨부 12건 동시 주문 실험은 초과 판매를 막는 기능 검증이다. 처리량 벤치마크가 아니다. 확장 실험에서는 충분한 재고와 요청별 키를 준비해 30초 준비 구간·정해진 측정 구간을 두고 성공 요청 지연을 기록한다. 품절 응답이 더 빨라서 전체 평균이 좋아지는 착시를 피한다.

## 확인 문제와 해설

**Q1. 가상 스레드 1만 개면 DB 연결도 1만 개가 필요한가?** 그렇지 않다. 대기 작업 수와 실제 DB 병렬 처리 한도는 별도이며 대기열도 제한해야 한다.

**Q2. Mono로 반환하면 자동으로 비차단인가?** 내부 호출이 블로킹이면 해당 실행 흐름은 여전히 기다린다.

**Q3. 평균이 개선됐는데 p99가 악화될 수 있는가?** 일부 요청의 긴 대기·GC·재시도로 가능하다. 분포를 확인한다.
